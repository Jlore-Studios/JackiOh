# Plan (sonnet, medium)

## Goal

A crash in a player's browser reaches the owners. The client sends one small report to a new `POST /api/client-errors` for each of the three triggers: an error `RouteErrorBoundary` catches, an uncaught `error` event and an `unhandledrejection`. At most 3 reports go out per page load. Lazy-chunk load failures and errors with no file of ours in the stack send nothing. The report holds the message, a trimmed stack, the route as a pattern and the catalog version. It never holds a hand, a board, a query string, a token, an address or an email.

The server size-caps the body, rate-limits it per address and per account, and raises `log_alert("client.error", …)`. `alerts.rs` already files the public issue (event, site, build, time) and sends the email with the details, under `ALERT_WINDOW_MS` and `ALERT_EMAILS_PER_DAY`.

No ruling is needed. Like `alerts.rs` and `bug_reports.rs`, this is operational, "not in SPEC, no R-row".

## Risks

- **Hidden information (rule 7):** the report is built from a whitelist of five fields. The server rebuilds its data from known fields only, and `routeOf` collapses ids. Do not send `info.componentStack` or any state.
- **Personal data in messages:** a thrown message could in theory hold anything the code put in it. It is capped at 300 chars and goes only to the private email. The issue body stays field-free by `alerts.rs` design.
- **Alert flooding:** `alerts.rs` allows one `client.error` notice an hour per process, so a second distinct crash in that hour is only counted as held. The address and account limits and the 3-a-page cap keep the log and the queue small. The queue (`ALERT_QUEUE`) drops on overflow but the log line stays.
- **Noise:** the chunk-failure regex covers Chrome, Firefox and Safari wording. Missing a variant only costs an alert; the builder must not widen it to match all errors.
- **`App` struct literal:** only `app.rs` and `tests/support/test_app.rs` are full literals. A compile error elsewhere means a file was missed.
- **Hourly cron / `/readyz`:** untouched, and no existing route is changed (rule 13).

## Open questions

- **Build field.** The issue asks for "the build (`x-deployed-commit`)" in the report, but the browser bundle never reads that header (only `GET /api/catalog` and `/healthz` set it, and no screen calls them). I did not add a second fetch and did not bake a commit into the Vite build. The server's own `deployed_commit` is already printed by `alerts.rs` as "on build …", and the Worker and its assets deploy together, so I used that. The cost is that a stale tab's report is stamped with the newer build; the client's own `catalogVersion` is sent to show the gap. A person who wants the bundle's own commit must decide on a Vite `define` fed from the deploy workflow, which is under `.github/`.
- **Numbers chosen.** The caps (300, 2000, 8192), the limit of 10 per address and per account every 10 minutes, and 3 per page are my picks. Adjust them if wanted.
- **Stackless errors are dropped.** This is the "no file of ours" rule applied to a missing stack as well, so a thrown string or an opaque cross-origin "Script error." sends nothing.

## Risks

- **Hidden information (rule 7):** the report is built from a whitelist of five fields. The server rebuilds its data from known fields only, and `routeOf` collapses ids. Do not send `info.componentStack` or any state.
- **Personal data in messages:** a thrown message could in theory hold anything the code put in it. It is capped at 300 chars and goes only to the private email. The issue body stays field-free by `alerts.rs` design.
- **Alert flooding:** `alerts.rs` allows one `client.error` notice an hour per process, so a second distinct crash in that hour is only counted as held. The address and account limits and the 3-a-page cap keep the log and the queue small. The queue (`ALERT_QUEUE`) drops on overflow but the log line stays.
- **Noise:** the chunk-failure regex covers Chrome, Firefox and Safari wording. Missing a variant only costs an alert; the builder must not widen it to match all errors.
- **`App` struct literal:** only `app.rs` and `tests/support/test_app.rs` are full literals. A compile error elsewhere means a file was missed.
- **Hourly cron / `/readyz`:** untouched, and no existing route is changed (rule 13).

## Open questions

- **Build field.** The issue asks for "the build (`x-deployed-commit`)" in the report, but the browser bundle never reads that header (only `GET /api/catalog` and `/healthz` set it, and no screen calls them). I did not add a second fetch and did not bake a commit into the Vite build. The server's own `deployed_commit` is already printed by `alerts.rs` as "on build …", and the Worker and its assets deploy together, so I used that. The cost is that a stale tab's report is stamped with the newer build; the client's own `catalogVersion` is sent to show the gap. A person who wants the bundle's own commit must decide on a Vite `define` fed from the deploy workflow, which is under `.github/`.
- **Numbers chosen.** The caps (300, 2000, 8192), the limit of 10 per address and per account every 10 minutes, and 3 per page are my picks. Adjust them if wanted.

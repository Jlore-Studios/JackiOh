### 2. The findings

1. **A shared hook adapter can look its function up under the wrong key** (`crates/luau/src/script.rs`, `direct_hook`, about line 413).
   - **What happens:** `hook_cache` is keyed by the Luau function's pointer alone. The adapter it builds keeps the `Site` of the first key it saw (`hook: key`). When the cache is shared across faces (`hooks::adapt_hook(.., across_faces)`), the adapter resolves that first key on the running face.
   - **The failure:** say a card's base face holds a function `f` under `cry`, and its Radiant face holds the same `f` only under a different key (`death`). The Radiant face's `death` reuses the adapter built for `cry`, and on a Radiant run it looks up `cry` on the Radiant table, finds nil, and the hook fails ("nil to function").
   - **What must keep working:** the sharing gaps 10 and 14 of #464 rely on (`Arc::ptr_eq` in `classicplus-070` Chaos Machine's tests: one function under two keys of one face; `classic-082` Sheeople and `classicplus-047` Jogg's Box: one function under the same key of both faces).
   - **The fix:** share an adapter only where the running face resolves the same function under the key the adapter looks up. For example, key the cross-face cache by (pointer, hook key), and keep the within-face sharing by pointer, since within one face both keys hold the function.
   - **Tests:** a fixture whose base face has `cry = f` and whose Radiant face has only `death = f`, run on both faces, alongside the existing gap 10 and gap 14 fixtures.
2. **An activation's `uses` skips L6's integer check** (`script.rs`, the activations declaration, about line 219). `Ok(Value::Number(n)) => ActivationUses::Count(n as i32)` turns 1.5 into 1, and wraps 2^32+1 to 1, with no error. `Value::Integer(n)` is cast the same way.
   - **The fix:** read it through `numbers::to_i32` (or the boundary's own integer check), so a non-integral or out-of-range count is a load error naming the card and face, as L6 requires everywhere else.
   - **Tests:** a fixture declaring `uses = 1.5`, and one declaring `uses = 4294967297`, each refused at load.
3. **The memory cap is lifted while readers build their answers** (`crates/luau/src/sandbox.rs`, `MemoryCap::lift`, about line 170). #870 scoped the cap this way for speed: under a cap, mlua runs every value the host builds through a protected call. That was the bulk of the slowdown, and the speed budgets in `docs/v0.4.0/README.md` §7 depend on it.
   - **The problem:** while a reader, `J.query` or `J.pool` builds its answer, a hook can hold more than `LUAU_MEMORY_BYTES`. So the claim in `crates/luau/README.md` and the code comment, that "the hook's next allocation past the cap fails", is not always true.
   - **The fix:** keep the speed. Make the README and comments say what does hold: a reader's answer is bounded by the state it reads, not by the script, and is counted; the script's own allocations stay capped, and its next allocation past the cap after a reader returns still fails.
   - **Tests:** a fixture script that calls a reader and then allocates past the cap, and fails.
   - **If you find a way to bound reader allocations without losing the speed,** measure it with `cargo jackioh luau bench` and the web wrapper's golden step against `main`, and write the numbers in the notes. Otherwise leave the code as it is.

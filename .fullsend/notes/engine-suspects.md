There is no R301 (§11 skips 295–309). The TS has no such citation: `packages/engine/test/rulings-a.test.ts:88` is `let nextIndex = 300;` with no comment. Fix (part 32's file): write the fixture index without the `R`, e.g. "(index 301 on)". One of the four problems that keep `spec check` red.
- **part 36, `pnpm vitest run --project web`: `view_for` (and `reduce`) cost 20–40× the TS engine's, so three sweeps outrun their timeouts under load.** `game/animations.window.test.ts` (both sweeps, `SWEEP_TIMEOUT_MS = 60_000`) and `practice/core.test.ts` "B38 two cores fed the same requests answer them identically" (120 s) time out in the full parallel run on a loaded 4-core machine; each passes alone with every assertion green (29 s, 28 s, 55 s at load average 9–11). Not a wrong answer, a cost. What the engine does, measured through the WASM bindings with `process.cpuUsage()` on a 69 KB `GameState` 140 random actions in: `seat_to_act` (the parse alone) 0.8 ms CPU, `legal_actions` 1.0 ms, `hash_state` 2.3 ms, **`view_for` 4.2 ms** (≈ 3.4 ms in `view_for` itself for an 8 KB view), `reduce` ≈ 7.7 ms wall; a sweep step calls `view_for` four times. Likely cost centres, not profiled: `redact_event` turns every event of the window into a `serde_json::Map` and back (`view_for.rs` `redact_event`/`rebuild`), `match_defs_in` walks the whole view as a `Value`, and `condition_active`/`preview_of` run per card. What the TS does: `packages/engine/src/viewFor.ts:1153` redacts on the objects themselves, and the whole 10-game, 140-action sweep took about 1.5 s (the test's own comment).

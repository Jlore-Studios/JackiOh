# `.harness/`: the night bot's switches

The bot reads these files from `main` and never changes them: `.harness/` is one of its
forbidden paths, so a change it makes here is reverted before review and refused at delivery.

| File | What it does |
|---|---|
| `config.json` | Every knob but the subscriptions: turn caps, time budget, review rounds, self-check rounds (`max_self_check_rounds`), auto-merge, the checks it runs (`"machine": false` leaves one to CI when the run is on the bot's machine), the required CI checks, how many times CI may run again on one head with no commit when a CI fix's failing check passes locally (`ci_reruns`, 1; such a run again costs none of the item's CI fixes, and past it a local pass is no answer; until #2948 it was how many times red CI's failed jobs were re-run before any fix, and the key reads the same; [Stopping red CI early](../bot/README.md#stopping-red-ci-early)), the suggestion cap, the quiet check, whether the status loop plans the night runs (`controller`, #1455), whether a Claude run resumes its own kept session (`resume_sessions`, #2748; [Handing work over](../bot/README.md#the-self-check-loop)), and how long an item waits for the subscription that owns it while only that one's 5-hour session keeps it (`hold_minutes`, 120, two hours since #2903; 0 holds nothing; also the most an approved draft waits its turn behind an overlapping pull request ahead of it, `bot:waiting-turn`, #2948) and the subscriptions an item never waits for (`hold_exempt`, Muse) (#2748; [Ownership and the hold](../bot/README.md#ownership-and-the-hold)), and every how many merged medium or hard bot pull requests one gets an after-merge spot-check by Opus, which blocks nothing and opens a follow-up issue for what it finds (`spot_check_every`, 5: a counter in the state file, not a draw; 0 checks none; #2748, [The after-merge spot-check](../bot/README.md#the-after-merge-spot-check)), and for fullsend (#2748, [Fullsend](../bot/README.md#fullsend)) whether an issue queued for a plain build that has open sub-issues is adopted as a fullsend tree by itself (`fullsend_adopt`, on; off builds it as asked) and how many times its reconcile may send one part back to the subscription that built it before it must fix the part itself (`fullsend_send_backs`, 1; 0 sends none back), and whether a run that changes code hands its lane to its own review run on the same subscription, which reviews, fixes and approves the change and turns auto-merge on (`own_review_run`, on; off builds, checks and reviews in one run, as Squishy does) and how long its lane stays reserved for that run once the build delivered (`own_review_reserve_minutes`, 30; after that the review waits for its subscription as owned work does, `hold_minutes`, or goes to its final audit) (#2748, the owner's decision of 2026-11-02; [The own review run](../bot/README.md#the-own-review-run)); with it on, a plan of an item that will be built takes a lane of its planner's own subscription when one is free, and that lane is kept for the build for the same `own_review_reserve_minutes`, so the plan, the build and its own review run go on one lane with the model that planned it, each in a fresh session (#2903, the owner's decision of 2026-11-03; [Difficulty and tiers](../bot/README.md#difficulty-and-tiers)), and whether the status loop records every subscription's usage over time on the `bot-usage` branch, each run's readings and row handed on by its delivery, for tuning these limits (`usage_history`, on; off, or left out, records nothing; #2749, [The usage history](../bot/README.md#the-usage-history)). Which changes wait for a person and which merge themselves (#2986, the owner's decision of 2026-11-04, amended the same day; [Safety](../bot/README.md#safety)): `review_paths`, the paths a person always reviews (the toolchain, lint, test and deploy configs, and the two scripts that deploy production); `migration_paths`, the migrations, which merge themselves unless one loses data (an `UPDATE` with no `WHERE` counts, #3009), changes who may read or write what, or edits or deletes a migration `main` has; and `lock_files`, the locks, which merge themselves (with their manifests) unless a lock gains a package `main`'s lock lacks or a changed `Cargo.toml` names a package its lock does not hold; a path none of the three names merges itself. How long a question with a suggestion waits for a trusted answer before the subscription and model that asked go ahead on it, filing the other options as issues (`decision_wait_hours`, 24; 0, or left out, never goes ahead), and whom `needs decision` assigns while it waits (`decision_assignees`: both people; #3009, [A question and its answer](../bot/README.md#a-question-and-its-answer)). The conflicted files of a merge of `main` the harness resolves itself, before any model sees them (`resolvers`: `take` `main`'s version, or both sides' lines with `union`, for a file that is truly an append-only list and none is now; or `run` a command that rewrites the file from the merged tree; [Planning](../bot/README.md#difficulty-and-tiers)), after Mergiraf, the syntax-aware merge driver the root `.gitattributes` names for TypeScript, JavaScript, JSON and YAML, which the work job registers (#2948). The easy rule's limits (`easy`) went with `difficulty:easy` in #2748 |
| `providers.json` | The subscriptions it may spend (Claude accounts, Codex, agy, Muse): each one's CLI, model, effort and tier (`medium` or `strong`; a `weak` one takes no work since #2748), any `extra_models` it runs (Sonnet, medium, on every Claude account, which switches between it and Opus), `fix_effort` for fix passes, `self_check`, its login (a secret's name, or `machine`), the runner its model job runs on (`runs_on`), hours and limits, its own `start_headroom` where it differs from the top level's (Muse's week has none), `last_hour` (claude-1, 4, 6, 7 and 8 spend their session's last hour past their 5-hour cap while nobody else spent it), `late_week` (from Sunday 17:00 until its week resets, claude-5 goes to 80% of its session and 90% of its week, with its sessions' last hours), `hard_cap` (claude-5's 90%: no cap on either window goes past it, its late week's and last hour's included, and a run stops a point under it, so no call spills past), how many run at once (`max_parallel` on GitHub's runners and `machine_parallel` on the machine, each apart from the other, and `plan_lanes` for the planning lane), how many items each subscription works on at once (its `lanes`, Muse's four; the Claude accounts' by `lanes_by_cap`, #2748: decided when a run starts from the 5-hour cap in force, up to 2 above 50% and 1 at 50% or under, so no Claude account names its own), the usage order (`priority`) and each tier's model order (`tiers`). A Claude account without its secret set sits out; `enabled: false` turns any one off ([Subscriptions](../bot/README.md#subscriptions), [the machine](../bot/machine/README.md)) |
| `trust.txt` | Who may command the bot, and at which level |
| `HALT` | Absent normally. Commit a file here (any content) to stop every model call at once; delete it to allow them again. `/harness halt` and `/harness start` are the everyday switch; this file is the one nobody but a committer can lift |

`config.json`'s `identity` names the other bot in the repository, Squishy (#60), whose issues the
night bot leaves alone and whose section the status loop draws; Squishy's own switches are in
[`.squishy/`](../.squishy/README.md). Its `modes` give the night bot `fullsend` (#505): the
`bot:fullsend` label or `/harness fullsend` splits an issue into parts (or takes the sub-issues it
has already) that land on one branch of its own, which a last run reconciles into one pull request
([Fullsend](../bot/README.md#fullsend)).

See [`bot/README.md`](../bot/README.md) for how the bot works.

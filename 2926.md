## Risks

- **Skipping a file another container is applying.** The fast path only returns when every listed file is already in the ledger. A row is inserted in the same transaction as its file's SQL, so a visible row means the file landed. An in-flight file is invisible, so the read falls through to the locked loop, which queues on `LOCK_ID`. The ledger transaction still takes the lock first, so concurrent boots still queue. The lock-wait assertion in step 5 guards this.
- **Transaction-mode poolers.** The new read is a plain autocommit statement, with no session state or session lock. It uses the same bound-query style as the loop.
- **A boot loop.** A wrong fast path stops every boot, since with one container there is no older instance. The edited-file and rewritten-checksum assertions pin the fall-through. `rehearse.sh` still greps `migrate: nothing to do` and `seed-catalog: wrote … at catalog version`, and both strings are unchanged.
- **One statement cannot touch a row twice.** Without the `IndexMap` dedupe, a duplicate id in an array or wrapper catalog file would fail the seed when both entries differ from the row. The last entry wins, as before. The duplicate-id test covers it.
- **`cost: null`.** The `coalesce` keeps jsonb `null` rather than SQL NULL.
- **Check constraints.** They are evaluated on the proposed row before conflict handling, so a bad tag is refused even for an existing row.

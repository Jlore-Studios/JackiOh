## Goal

When R90's bound (`MAX_CHOICE_COMBINATIONS`, 64) drops some of a hand card's play-choice combinations, and `legalActions` lists plays of that card, the viewer's own hand card in `viewFor` carries `choicesTruncated: true`. Otherwise the key is absent, so every view and every `legalActions` list stays byte-identical. The engine also exposes `listed_play_choices`, which returns the same combinations plus a `truncated` flag, for the AI or tools to read. Lists and their order do not change. R90's note and §10.8 say this, with no new ruling, as the issue asks. The generated `CardView.ts` is committed.

Decisions the task left open (alternatives rejected):
- **Where the marker goes:** a view key, like `counteredOnPlay`. I did not put it on the `play` action body: the client sends a listed action back as its intent, and the server and replay logs carry it. I also did not add a separate list to `legalActions`: that needs a new wasm export, a new field in the server's `View` message and web bindings, while `viewFor` already reaches every client.
- **A boolean, not listed/total counts:** a total needs a second copy of the enumeration's counting rule and overflows on wide crosses. The listed count is simply the number of listed plays.
- **Scope is plays from hand.** Activations (`activate_actions_for`) and graveyard plays are not marked (see Open questions).
- **Name:** `choicesTruncated`, the issue's name.

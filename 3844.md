## Risks

- **A 403 from something other than a key change would delete a live subscription.** Possible causes are a wrong server clock making the VAPID token's `exp` bad, or an operator setting a different but valid key pair by mistake. The cost is bounded: the device turns push on again, and the email channel is untouched. The issue chose this trade (RFC 8292 §4.2 and FCM answer 403 for key mismatches). The alternative, a counter, would need a migration.
- **No other status becomes gone.** 401, 429 and 5xx stay `Failed` and are retried (the 429 test pins this). Do not widen the match to `is_client_error()`.
- **No determinism or replay risk.** The change is in the server crate, outside the pure crates. There is no wire change, so `apps/web/src/wire` stays clean, and no database change, so the Postgres suites do not run.
- **The "Gone" log line.** `daily.push.gone` now also fires for 403. Nothing in the repo matches on it, so leave it.

## Open questions

- **Not in this plan: a follow-up for the web client.** `apps/web/src/daily/push.ts` `enablePush` reuses the browser's existing subscription (`getSubscription() ?? subscribe(…)`). After a key change, a device that turns push on again re-posts its old, key-bound subscription, which is answered 403 and deleted again. Browsers also refuse `subscribe()` with a different `applicationServerKey` while an old subscription exists. The client should unsubscribe a subscription whose `options.applicationServerKey` differs from the server's `vapidPublicKey`, then subscribe again. Nothing in this issue asks for it, and it touches `apps/web`. A person should open it as a separate issue, which the night bot can build, before the VAPID keys are rotated. The issue's "don't rotate the VAPID keys" holds until then, even with this fix.

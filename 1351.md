## Risks

- **Determinism and replay.** A muted emote still enqueues `Task::Emote`, so the log and the hash match an unblocked game. Never put the check in `Task::Emote` or in the engine.
- **Lock across `.await`.** In step 2, take `self.lock()` only after `one_tx!` resolves, as written.
- **Arm race.** The registry inserts the actor synchronously right after `create_match_actor` (registry.rs l.316, l.467). The read runs after `persist_clocks().await`, so a block committed while the match is being created is practically never missed by both the read and the push. `|=` stops a stale `false` from undoing a push.
- **Hidden information.** No new data reaches a client. A muted pair still sees R1127's public `emoted` event when a card hears it: the hero shakes, and the log line names no emote.
- **Telemetry.** The early return skips `on_emote`, which the ruling states.

## Open questions

These are decisions this plan makes, each with the alternative it rejected; a person may overturn them:
1. **The mute lasts the actor's life.** Rejected: re-reading on `DELETE /api/blocks` and unmuting mid-match, which needs a second push and has an ordering race.
2. **A failed block read at arm leaves the match unmuted.** Rejected: failing closed, which would mute every match during a store fault.
3. **A muted emote is left out of R1442 telemetry.** Rejected: recording it, which would skew `reply_to_opponent_ms` with replies to emotes nobody saw.
4. **A person's muted emote is not offered to the bot's persona.** Its reply would be muted anyway.

Out of scope, for a person to file if wanted: nothing refuses a post-game rematch offer (`api/rematch.rs`) between a blocked pair, because the server reads no blocks there.

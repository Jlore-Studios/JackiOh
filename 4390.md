## Risks

- **A reader that needs a closed invite.** None in `crates/server/src`.
  - `daily_invites_get` has one caller, `open_challenge`, which already 404s a non-open or lapsed row.
  - `accept`'s `daily_invites_close` already answers 404 when the row is gone.
  - `reopen_seek` clones the claimed row in memory and re-inserts it, so a purge between claim and reopen loses nothing.
- **A failing purge blocks the sweep.** The purge shares the sweep's transaction, so a store error also rolls back the expiry and `daily_games_due`. `notifications_purge` already behaves this way and the issue asks for it. The failure shows as `daily.sweeper.failing`.
- **A share written just as the purge takes the log.** The next pass deletes it, and nothing reads it meanwhile.
- **Clock.** The invite purge takes the sweep's `now` (`app.daily.now()`, test offset included). The share step reads no clock.
- **No migration.** Don't add one: it would make this item hard. If a plan check seems to need an index, stop and say so in the report.

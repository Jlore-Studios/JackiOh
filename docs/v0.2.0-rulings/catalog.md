# Patch v0.2.0 rulings: the catalog workstream (R480–R499)

Rows in SPEC §11's format, for the docs workstream to port into §11. Each is proved by a test named
after it and indexed in `packages/engine/test/rulings.test.ts`.

| R | Topic | Ruling | Cards affected |
| --- | --- | --- | --- |
| R480 | Tokens named by their tag | The eight Pancake tokens and the ten AI generated cards reach play only as members of a pool a card names by its tag — "a random Pancake token" (Classic+ #12 The Mother Pancake, #13 Mommy Barker), "a random AI generated card" (#43 AI Slop, #78 Claude's Datacenter) — never by name, so R279's rule that every token is named by some card counts a text that names that pool as naming each of its members. A card's `refs` still lists only the cards its texts name by name (R279, both ways), and The Coin, which a rule deals (R244), is now also named by Classic+ #42 KY's Test ("3 The Coins"). The five Grapes are named one by one in Two Grapes' and Vine of Grapes' odds, so they need no pool rule | §5, §7, R244, R279, Classic+ #12, #12.1–#12.8, #13, #42, #43, #65, #66, #78, T-AI-1–T-AI-10 |
| R481 | A catalog that grows is granted | Everyone owns every card (§9.1), and R111's launch grant rides only the pending → active transition, so an account already active when a patch adds cards would never own them. When `app.settings.catalog_version` changes — `db:seed-catalog` stamps it after writing every card row of the new version, in the same transaction — every active account is granted the launch quantity of each non-token card of the new version it holds no `launch` grant for, through `app.grant_launch_collection_all` and the ledger (reason `launch`, ref `launch:<version>`, migration 0015). It is idempotent: the same stamp again, or a round trip through another version, grants nothing twice; a pending account waits for its own activation; a card a later catalog drops is never taken back | §9.1, §9.4, R111, every Classic and Classic+ card |
| R482 | How a card writes its tunable numbers | B3.4 rule 5 declares a card's tunable numbers as `params` and writes them `{key}`. Every item of a Classic or Classic+ card's Numbers line (docs/classic-sets.md B6, B7) is one param `{ key, base, radiant, better, step, min, max? }`: `better` "up" when more is better for the card's controller (an item with no arrow is its effect's own strength, "up"); `step` as stated, else B3.4's default from the base value (1 up to 5, 2 for 6–12, a quarter above); `min` as stated, else 1, or 0 for a number printed 0, and never so low that the effect stops (Argusland's divisor stops at 2); `max` only when stated, 100 for a percentage. The ten AI generated cards (B8) have no Numbers line and declare none: their numbers are printed, and Degrade has fewer options on them. The number is written in each face's text that shows it and nowhere as a literal: `{key}` for the number alone ("Deal {damage} damage."), `{key|singular|plural}` for a count and the words that agree with it ("Draw {draw|card|cards}." prints "Draw 1 card." and "Draw 2 cards."), and a sentence after a count that would need an agreeing pronoun says "Each …" ("Each costs (0)."), so a text reads right at every value a Degrade or an Upgrade can move it to; a Radiant-only number is written in the Radiant text alone, with the same value on both faces. A numbered keyword (Armor, Lucky, Brittle, Spell Damage) and an Echo, Tribute or Activate count is no param: B3.4's X change tunes those. `fillParams` (packages/shared) fills a face from its printed values or an instance's current ones, and R277's diff, R276's check and the text tests read a face through it | §5, R276, R277, B3.4, every Classic and Classic+ card with a Numbers line, T-AI-1–T-AI-10 |

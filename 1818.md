## Risks

- **GIF share and the user gesture.** `navigator.share` only works during a click, so `send` must call `shareGif` synchronously in the click handler. Do not put an `await` or an `import()` before it.
- **`setPhase(ready)` before the share.** It removes the failure alert at once. A dismissed sheet (`AbortError`) leaves the phase at `ready`, as today.
- **Creator retry delay.** The retry goes back through the effect, so it waits `CHECK_DELAY_MS` before checking; the test's `waitFor` covers that. The stale-answer guard (`asked`) still drops any older answer.
- **Retries are manual only.** Nothing retries on a timer, so nothing can loop.
- Hidden information and rule 7 are not involved: each change only re-runs a request the client already made.

## Open questions

None needs a person. Decisions I made, with the alternative I rejected:
1. **Label "Try again" on all three**, not "Share again" on the GIF. "Try again" is the app's established label (#1706, #1766, #1783) and already has a zh-CN entry; "Share again" would need a new one.
2. **Stats Try again only on a load error**, not also when the server has no stats for the card. Re-fetching would return the same empty answer, so it would not move the player on.
3. **The creator's retry re-runs the existing effect** through an `attempt` counter, not a separate immediate check. That avoids a second code path, and the 300 ms wait is negligible.

1. **Add the flags to `run.sh`.** Put this comment and variable directly above the "Built once:" comment block (just before `echo "--- build (jackioh-server and its store tests) ---"`):
   ```sh
   # The engine and the cards compile at opt-level 0 here, not the test profile's 2 (Cargo.toml): these

   cargo test $PROFILE_FLAGS --manifest-path "$REPO/Cargo.toml" -p jackioh-server --test server_store "$@"
   ```
   Do not leave any `cargo` call in the script without `$PROFILE_FLAGS`. The flags change the profile, and a call without them rebuilds the workspace crates at opt-level 2 (about 3 minutes).

5. **Leave everything else in `run.sh` alone.** In particular keep `DB_SHARDS` at its default of 3. I ran 6 and 8 databases on the same warm build and the test phase stayed at about 50 s (the 3-database baseline was 52 s), so more shards only add load.

No new automated test is needed, because the change is a CI script's build flags. The existing 682 `store::` tests are the proof, and they must still pass. Run these in order:

   - Then run `awk '/--- cargo test/{f=1} f && /Compiling/{bad=1} END{exit bad}' /tmp/db.log`. It must exit 0, meaning no `Compiling` line after the `--- cargo test` header (only `Finished` lines in well under a second). Any `Compiling` there means a `cargo` call is missing `$PROFILE_FLAGS`.

## Risks

- **Flags on some calls only.** A `cargo` call without `$PROFILE_FLAGS` recompiles everything at opt-level 2 and undoes the saving, and the awk check in Tests catches it. Add the flags to any `cargo` call you add later.
- **Cache.** `Swatinem/rust-cache` restores dependencies only, and the flags change only the engine's and the cards' profiles, so the cached dependencies stay valid.
- **Slower tests at opt-level 0.** In my runs the test phase was 52 s at 0, 1 and 2, because the tests wait on Postgres and play no game. `crates/engine`, `crates/cards` and `crates/ai` source and purity are untouched, and no replay or hash is affected.
- **A cold CI cache.** The CI run may have recompiled every dependency, and nothing outside `.github/` helps that. The 108 s is the build's floor on the critical path (engine 46 s, then the server library 37 s, then the `server_store` test 25 s).
- **Measured on a local box, not CI.** The local numbers come from the planner's own box. The CI report that raised this issue also counts checkout, toolchain and cache restore, which the script does not. Read the next `ci-duration` report to confirm.

## Open questions

- **A second pass if it is still slow.** If the next `ci-duration` report still shows this job over 5 minutes, a person should look at the db-suite job's Rust cache first. Splitting the suite into two matrix entries in `.github/workflows/ci.yml` would save at most about 25 s, because each entry compiles again. No `.github/` change is needed for this plan.
- **Left alone on purpose.** `StoreHarness::postgres()` in `crates/server/tests/store/contract.rs` truncates the tables, and the `reset()` that follows truncates them again. Dropping the first truncate would save about 50 ms of Postgres time for each of the 304 Postgres tests, but it changes the test harness for a small gain. I did not plan it.

### 9.4 Accounts, collection, loadouts

- Managed auth provider; `profiles.status` in pending, active, banned. A pending account can log in, verify its email and see the code screen, and nothing else: no collection, loadout, queue or match. Redeeming an invite code flips pending to active.
- Codes: 16 characters (80 bits) from a 32-symbol alphabet without 0/O/1/I/l, formatted `XXXX-XXXX-XXXX-XXXX`, stored hashed. Redemption first refuses an account owing the age check or agreement to the terms in force, costing no attempt ([[R757000]], [[R757001]]); then it is one server-side transaction: (1) reject unless the account is pending with a verified email; (2) reject if this profile made more than 5 attempts in the last hour; (3) reject if this IP hash made more than 20; (4) log the attempt either way; (5) look up by hash and reject if revoked, expired or exhausted; (6) increment uses and set the account active, atomically. Missing, expired and exhausted codes return an identical error in identical time. Steps 2 and 3 are the only blocks: they hold one profile or one address off for the rest of their hour, and no count of failures across addresses pauses redemption for everyone, since a guess spread over many addresses cannot find an 80-bit code and a breaker it could trip would shut sign-ups for every honest player; only the operator's switch pauses it ([[R4131000]]). Trusted devices (a signed device token that skips the code screen after a reinstall) are optional and never authorise an account.
- The client's code screen and sign-in screens are UX over the rules above and decide nothing the server does not. The code is typed into one field drawn as four groups, read exactly as the server reads it ([[R191]]), and submitted only when complete, so a partial code costs no attempt. The two-step code is one field drawn as six boxes, read as digits only ([[R4669000]]). The screen shows how many attempts the account has left in the window and, with none left, when one comes back. A refusal at steps 2 or 3 is shown as a rate limit with its wait ([[R192]]), never as the identical error. A code refused with [[R145]]'s identical error is not sent again until the player changes it, since it cannot turn good and each try counts, and the field is locked while a code is being redeemed. Sign-in, sign-up, confirmation resend, password reset and a signed-in player's change of email (from the account page (`/account`), [[R663]]) go straight to the auth provider ([[§9.2]]), except a sign-in by username, which the server makes for the player so that no address reaches the browser ([[R1443]]). Every refusal is mapped to the client's own sentence, and none reveals whether an account exists ([[R160]], [[R192]]). Emailed links are read once and scrubbed from the address bar ([[R193]]), and a session is renewed or ended as [[R194]] says. Every screen on the way (landing, sign-in, reset, the code screen, the gate's own panels, a screen whose code failed to load, and a check that runs long) offers a way back. The per-IP limit of step 3 counts the address [[R190]] names.
- Usernames. Every account has a username: a base name and, when another player holds that name, a numeric tag (`Max`, `Max#1`, `Max#2`). The base is `USERNAME_MIN_LENGTH` (2) to `USERNAME_MAX_LENGTH` (16) user-perceived characters of letters, digits, `_` and a letter's combining marks, in one script or a mix a language needs, and is stored in its NFKC form ([[R1432]]). A light profanity filter is the only content check, and no name is reserved ([[R1433]]). Two names clash when their NFKC case folds match: the first player to pick one gets it bare and each after the lowest free tag, and a new account starts as `Player#n` ([[R1434]]). A player changes their username at most once every 24 hours, through a preview the server answers with the exact username a save gives or why it refuses, and an account that has just turned active is asked for one before anything else, with a way to skip ([[R1435]]). A username is a label only: the server, the database and every request key a player by profile id, and every read that shows a player carries both ([[R1436]]); the one request that names its caller by username is a sign-in by username, made before there is a token, which the server turns into the provider's session for that profile ([[R1443]]).
- Friends. An active account adds a friend by their exact username, `name#tag` as [[R1434]] tags it: there is no search and no list to browse. A request by a name nobody holds and a request between two players either of whom blocks the other get the same answer, not found, so a request never tells whether a name exists or has blocked its sender. A request to oneself, to a friend, a second one to the same player, or one past `MAX_FRIENDS` (200) friends is refused with its reason, and requests past `FRIEND_REQUESTS_PER_HOUR` (20) in an hour per account and `FRIEND_REQUESTS_PER_ADDRESS_PER_HOUR` (60) per address ([[R4008001]]) are refused as a rate limit. A request the other player has already sent the requester is accepted at once, a mutual add. Accepting makes the friendship and deletes the request; declining it, and its sender canceling it, delete it; either friend may remove the friendship, which cancels every open challenge between the two, either way, and frees its room, as a block does ([[R1689000]]). A friend is keyed by profile id and shown by username ([[R1436]]), and a request or a friendship is readable by its own two players only.
- Blocks. A player may block another player. A block removes their friendship, every request and every replay share between them, either way, ends at once a watch of either by the other, and while it stands stops new requests, challenges, chat and replay shares between the two, both ways ([[§9.5]]); unblocking lifts it and restores nothing. A match between the two relays neither one's emotes to the other from the block to the match's end, while the game plays on as before ([[R1351000]]); a block never changes who the queue pairs. A player's blocks are readable by that player alone.
- Presence. Every signed-in request of an active account that passes auth and the gate is a heartbeat, which the server records at most once a `PRESENCE_TOUCH_EVERY_MS` (30 s); a client sends `POST /api/presence` only once `PRESENCE_HEARTBEAT_MS` (45 s) has passed with no signed-in request of its own ([[R3210000]]). A friend's status is in a match while a live match, a Conquest series or a co-op game ([[§13]]) holds them, online while their last heartbeat is within `PRESENCE_TTL_MS` (90 s), and offline otherwise. Heartbeats are the server's alone, and a status reaches only the player's friends. A friend's row also says, to a friend alone, when an offline friend was last seen, the turn of the 1v1 game they are in while the viewer may watch it, and the code of an online friend's lobby with an empty seat ([[R3732001]]). The client reads the friends list again every `PRESENCE_HEARTBEAT_MS`, the pace a status changes at, and a screen other than Play together only while its friends panel is open; the server answers it in one transaction by a fixed number of reads, whatever the number of friends. The unread counts and the challenges are read together every `SOCIAL_POLL_MS` (10 s), in one request shared by a tab's screens ([[R3210000]]). A signed-in tab also holds one live socket, `/ws/social`, signed in as the match socket is and checked again every R194 window while it stays open, over which the server sends that account's own challenges and unread counts whenever they change, and says that a chat message was sent or that its friends list changed, with nothing in it another account may not show it; while it is up the tab sends neither read and reads the friends list again at once on such a word, and the polls run only while it is down ([[R3214000]]). A hidden tab sends none of these reads, nor an open chat's, the live-game banner's, the rematch's and co-op Play again's status or the series banner's: each reads once when the tab shows again and goes on at its pace, while the queue's reads ([[R897000]]) and the waits whose place the server expires keep running ([[R3205000]]). A tab hidden for `HIDDEN_QUIET_MS` (two minutes) goes quiet: it closes its live socket and sends no heartbeat, so its friends see it offline `PRESENCE_TTL_MS` after its last request and its server may sleep, and it opens the socket again when it shows ([[R3576000]]). A shown tab with no input (a pointer, a key, a wheel, a touch) for `IDLE_QUIET_MS` (ten minutes) goes quiet the same way and pauses its polls, and its next input, or its turning visible, brings it back with one read ([[R4691001]]).
- Notifications. The server keeps a feed of what happened to each account until the account has seen it, and it is the channel that is always on ([[§9.13]]): a daily game waiting on the account's move, one it played ending (on time and by concession included, with the result it sees), a daily challenge to it and the answer to one it sent, a friend request to it and the accept of one it sent, a friend's lobby invite, listed while the lobby is open and unstarted, and a replay a friend shared (not again for one already shared, [[R4391000]]). Each is one row, written by the server where it handles the event and after it, by the account that did it and about what (a game, a challenge, a request, a lobby, a replay); a newer row replaces the account's unread one of the same kind, by the same player, about the same thing, so a game's next move never stacks; nobody is told of their own act, and a block either way writes nothing. An account keeps its newest `NOTIFICATIONS_KEEP` (100) rows, and the daily sweep deletes those older than `NOTIFICATIONS_KEEP_DAYS` (30). The account reads its own rows a page at a time, newest first, and marks them read up to one or all; each new row reaches its tabs' live sockets as it is written, and the social read counts the unread ones ([[R4039000]]). A row also counts as seen as soon as its owner opens or answers what it is about: reading a daily game's board (or sending an action there) marks that game's rows read, answering a daily challenge or a friend request, entering a lobby and opening a shared replay each mark that subject's row read, and the game-ending row told to the player whose own act ended it is written already read; each stays listed under Recent. A `lobbyInvite` whose lobby is gone, started or expired counts as unread nowhere ([[R4233000]]). The inbox shows it ([[§9.5]], [[R4039001]]).
- Collection is an entitlement ledger (`collection` plus append-only `collection_grants`); catalog is static, versioned, shipped with the client; stale catalog version is rejected at save and at every door into a match: the queue, a room's join, a co-op room's join and a rematch offer ([[R1638000]]); a queue ticket enqueued on an earlier version ends at the next sweep ([[R5159000]]). The catalog version is the latest card patch's ([[R105]], [[R388]]): every patch's snapshot of the whole catalog is kept, in order, as its delta from the patch before it ([[R5268000]]), so an older version of a card can still be read (the collection's History, a public Patch notes page, and the server's `GET /api/catalog/:version`), and a match folds under the version it started with. Becoming active grants the starter cards ([[R111]], [[R1310000]]), and every other card comes as [[§14]] says: a patch's new cards are granted to nobody ([[R1310001]]). Until the economy went live ([[§14.12]]), the launch grant was every non-token card and each patch's new cards went to every person's active account ([[R481]]). Every collection change writes `collection` and `collection_grants` in one transaction, and no client path writes either.
- Decks and trios. A player saves up to `MAX_SAVED_DECKS` (10) named decks and builds up to `MAX_SAVED_TRIOS` (5) trios from them; a trio is three of the player's saved decks, in order ([[R250]], [[R252]]). Both are drafts, so a save checks structure and never legality: a deck's **D1** name of 1 to `DECK_NAME_MAX_LENGTH` (40) characters, **D2** at most `DECK_SIZE` cards, **D3** every card a deckable card of the catalog, **D4** at most `MAX_COPIES` of a card, **D5** the deck's `portrait` `null` or a known portrait id ([[R641]]), and on the server one the account owns ([[R1827000]]); a deck also carries its playmat, backdrop and card back picks, each `null` or an id of its kind ([[R1297000]]), and on the server one the account owns ([[R1833000]], [[R1834001]]); a trio's **T1** name, **T2** three slots, any of them empty, **T3** no deck twice. An incomplete deck, a card the player does not own and a trio whose decks share a card are all kept, and judged when queued. A card is its catalog id: Radiant is a flag on a card in play ([[§5.2]]), never a second card ([[R251]]). Every deck and trio has an id the client mints, and saving one is an idempotent upsert of it alone ([[R256]]); the builder's autosave sends its saves and deletions in one request of at most `DECK_SYNC_ITEMS_MAX` (30) items, each checked, saved and answered as it would be alone ([[R3212001]]); deleting a deck empties the trio slots that held it. The catalog version the client holds is checked at save. A deck travels between players as a versioned deck code ([[R255]]), and a trio with its three decks as a versioned trio code ([[R339]]); both are at version 2 since patch v0.2.0, which writes each card's number with its set (Core n, Classic 1000 + n, Classic+ 2000 + n, Meditative 3000 + n, Meditative+ 4000 + n, [[R1410]]), and a version 1 code, which every code minted before it is, still reads as Core numbers; importing one makes the decks and the trio together, under both caps, or makes nothing and says how many slots it needs ([[R340]], [[R341]]). The single loadout of three decks that came before became three saved decks and one trio ([[R254]]). Each save of a deck keeps a version of its name and cards on the account, a save within `DECK_VERSION_DEBOUNCE_MS` (60 s) of the newest replacing it, at most `DECK_VERSIONS_KEPT` (20) per deck, and restoring one saves it again as a new version, so a restore can be undone ([[R2100000]]).
- Age and terms. A person may hold an account from `MIN_ACCOUNT_AGE_YEARS` (13). Sign-up asks the month and year of birth, nothing chosen and no age named, and an answer under the minimum makes no account and is remembered on the device; the server counts the age again, deletes an account under the minimum the way "Delete my account" does, and keeps only that the check passed, when and against which minimum, never the birth date ([[R757000]]). Sign-up needs an unticked box agreeing to the Terms and the Privacy Policy, and each account's agreement is kept per version (`TERMS_VERSION`, both pages' dates) with its time; an account that owes the version in force is asked again on the gated screens, never on `/account` or mid-match ([[R757001]]), and on `/replays` before its online half ([[R970000]]). A second change to a page on one day gives its half of the version a letter, and a test holds each version to the pages' words ([[R970001]]). No request records presence while the account owes the terms ([[R970002]], [[R3210000]]).
- An active account also keeps its tutorial progress ([[§9.10]], [[R320]]): the player reads its own row, and the server merges into it and never removes a lesson.
- An active account also keeps its game settings ([[§10.11]], [[R633]]): the player reads its own row, and the server replaces a group of it only with a strictly later one ([[R634]]).
- Queue rules, checked by one validator module shared by client and server, when a deck or a trio is queued or brought to a room: **L1** a trio holds exactly 3 decks; **L2** exactly `DECK_SIZE` (25) cards per deck, which a deck saved at 20 before #1705 fails until it is filled ([[R1705001]]); **L3** at most `MAX_COPIES` (1) of a card per deck, a Core card and its Training Grounds Legacy card counting as two ([[R2511001]], superseding [[R2195000]]), no Token-tagged cards and no card of a set that has not shipped ([[R1420]]); **L4** a card id appears in at most one deck of a trio, so one deck may hold a Core card and another its Legacy card; **L5** copies never exceed the quantity owned; **L6** every card exists in the current catalog version and is not banned. A Best-of-1 deck must pass L2, L3, L5 and L6, and a Conquest trio all six ([[R253]]). A queue-time failure names the deck and the card. The chosen deck or trio is frozen into the queue ticket or the room.

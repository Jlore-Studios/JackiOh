**[[R2478000]] refuses a spent account before the database and counts socket upgrades (issue #2478, 2026-10-30)**: the API's limit of 300 requests a minute per account ([[R109]]) was checked after the router had read the caller's profile, so a request past it was refused with 429 only after it had checked one of the pool's ten connections out, and one signed-in client in a loop kept them all busy while live matches waited to save their moves; the match, co-op and watch sockets read the profile too and were counted by nothing, `WS_MAX_CONNECTIONS_PER_ADDRESS` limiting the sockets open at once and not how often they reopen. The server now remembers, in memory and at most `KNOWN_PROFILES_MAX` users, the profile id each verified auth user last resolved to, and refuses a request from a known account whose budget is spent before it opens a transaction, with [[R192]]'s 429, logged and counted as [[R1717000]] says; the map holds an id only, so every request it lets by still reads the profile and meets [[§9.4]]'s gate, a user it does not know still reads the store and a new account is still created lazily, and two tokens of one account still share one bucket ([[R157]]). Each match, co-op and watch upgrade whose token verifies counts as one request against that bucket, and one past it gets the `forbidden` frame and close 4429, which the client retries on its backoff ([[R1441]]), a refused upgrade not being counted. An HTTP 429 before the handshake was rejected, since every refusal of [[R148]] arrives after it, and so was caching whole profiles, which would let a stale ban pass the gate. It takes R2478000, the first number of issue #2478's block, edits [[§9.8]] and amends [[R148]].

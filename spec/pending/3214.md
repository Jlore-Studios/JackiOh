**[[R3214000]] Challenges, unread counts, chat and friends-list changes arrive over one live socket per tab, and the polls run only while it is down (issue #3214, 2026-11-06)**: tracker #3204 asks for less compute, better security and faster traffic, and after [[R3210000]] every signed-in tab still read `GET /api/social` every `SOCIAL_POLL_MS` and an open conversation every `CHAT_POLL_MS`, on every screen, whether anything had changed or not. Each tab now holds one socket at `/ws/social`, signed in as the match socket is (the subprotocol, never the address, [[R1379000]]; one request against the account's budget, [[R2478000]]; §9.4's gate), capped at `SOCIAL_SOCKETS_PER_ACCOUNT` per account and counted per address apart from the game sockets, and checked again every `SOCIAL_SESSION_CHECK_SECONDS`, one [[R194]] window, so a revoked session or a ban closes it with 4401 or 4403. The server sends it `social`, that account's own `GET /api/social` answer, after each change to its challenges or unread counts (a lapse among them) and in answer to a hello; `chat {friendId}`, with no body, when a message between it and that friend is sent; and `friends` when its friends list changes, a block of a stranger telling the stranger nothing. While it is live the tab polls neither read and an open conversation reads on its friend's `chat` frame; once it drops the polls run as before, and it reopens on the match socket's backoff. Server-sent events, message bodies in the frames, pushed friend statuses, a per-address count shared with the game sockets, closing the oldest socket past the cap and a token-only session check were rejected. It takes R3214000, the first number of issue #3214's block, and edits [[§9.4]] and [[§9.5]].

**[[R3209000]] Requests that arrive together share one provider session check, and a silence about a session is remembered briefly (issue #3209, 2026-11-06)**: tracker #3202 asks for less compute, better security and faster traffic, and a burst of requests had become a burst of calls to Supabase Auth: [[R194]]'s session check remembered only a live answer, so requests that arrived together with none remembered (a screen's first reads) each asked `GET /auth/v1/user`, the admin lookup of [[R159]] did the same per user, and during an outage every request waited the provider's full 30 s timeout before its identity stood. Concurrent checks of one session of one user now share one call and its answer, as concurrent admin lookups of one user id do; a silence about a session is remembered for `AUTH_SESSION_OUTAGE_CACHE_SECONDS` (15 s, asserted no longer than the 30 s live window), inside which a request answers at once as it would after the wait; the call by token gives up after `AUTH_SESSION_CHECK_TIMEOUT_SECONDS` (5 s), which covers tier 3's lookup too since it shares the call, while the sign-in grant and the admin calls keep `AUTH_PROVIDER_TIMEOUT_SECONDS`; and the published keys are decoded once per fetch and kept with the set under [[R1144000]]'s refetch rules. Answers are keyed by user and session, so a session id under two users is two checks. Rejected: a 30 s outage memo, since a provider that recovered would wait out a whole window before an ended session is refused; a memo shared across users, since one user's 429 would skip every user's check; and an outage memo or the shorter timeout for the admin lookup, since the issue asks them only of the session check and R159 wants a just-confirmed email believed at once. It takes R3209000, the first number of issue #3209's block, and amends [[R194]].

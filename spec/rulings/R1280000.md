[[R646]]'s promotion snapshotted `catalog.json` as each fragment's adding commit left it, and refused when that catalog did not change exactly the fragment's cards. `patches check` lets a fragment change after it merged, and it holds a card to exactly one pending claim, so a later pull request that changes a card an earlier fragment claims must leave the change under that claim. The first such change made every promotion after it refuse: patch v0.3.8 to v0.3.15 waited behind one from 2026-10-15 to 2026-10-19, with the catalog version at v0.3.7b throughout.

So a patch's snapshot is the patch before it with the cards its fragment claims as `catalog.json` holds them now: a claimed card takes its entry there (none, when the catalog no longer holds it), every other card keeps the one before, in the catalog's order, a card only the patch before holds keeping its place after the card it followed. Since `patches check` proves the claims cover every change from the newest shipped snapshot exactly once, the newest snapshot is `catalog.json` itself, byte for byte, and each patch's card-by-card changes are its own claims. The patches ship in the order of the first-parent commit that added each fragment, as before, dated by that commit and recording it in `shipped.json`; fragments one commit added ship in the order of their files. A card changed again under its claim, a fragment that grew, or two fragments in one commit ship like any other, so a merged pull request whose `patches check` passed cannot stop the queue.

A refusal still writes nothing, and `.github/workflows/patches-ship.yml` then opens an issue (or comments on the one open) with the failed run, queued for the night bot, rather than failing quietly on every push. The versions this fix shipped at once, v0.3.8 to v0.3.14, hold snapshots the claims built rather than a commit's catalog; no game was stamped with them, since the server stayed at v0.3.7b, so no replay folds under them ([[R767000]]).

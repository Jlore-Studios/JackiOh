Several card patches are built on separate branches at once (issue #63), so branches never edit `patches.json`, the snapshots, `index.json` or `shipped.json`: a branch changes `catalog.json` and adds one pending fragment, `packages/cards/patches/pending/<version>.json`, holding `{ version, title, sources, notes, cards }`, where `cards` lists the catalog ids the patch creates, changes or removes and `version` is a bare patch number (`^v\d+\.\d+\.\d+$`) or a micro `vA.B.Y` ([[R650]]), never a revision. `patches check` (run in CI, in the `validate:catalog` step) fails naming the card when a catalog entry differs from the newest shipped snapshot without exactly one fragment claiming it, when a claimed card does not differ, when a fragment's version is neither a bare number nor a micro `vA.B.Y`, when a fragment claims no card, or when a fragment's `title`, `sources` or `notes` is empty, since they become the shipped patch's ([[R388]]); an entry differs when its bytes do, key order included; the catalog with every pending-claimed entry reverted to the newest shipped snapshot equals that snapshot. `patches ship` (idempotent, needs full history) promotes every fragment on `main` in the order of the first-parent commit that added it: it appends the patch — the fragment's version (a micro `vA.B.Y` first named after the then-newest patch, [[R650]]), or `<version>b`, then `c`, and so on when that name already shipped, since a shipped version never reopens — dated by that commit's UTC day, with `title`, `notes` and `sources` from the fragment, snapshots `catalog.json` as that commit left it (so a later patch's snapshot includes the earlier ones' changes, and its card-by-card changes list only its own cards), records `{ version, commit, blob }` in `shipped.json`, deletes the fragment, regenerates the derived files and bumps the catalog version to the newest patch; with no fragments it changes nothing. It writes nothing unless each adding commit's catalog differs from the patch before it on exactly the cards its fragment claims, one commit adds one fragment, and the last snapshot is `catalog.json` as it stands. `.github/workflows/patches-ship.yml` runs it on every push to `main` touching `pending/` and opens the promotion as a pull request that merges itself once CI passes, closing any older promotion it supersedes. Tests that read the real history hold on a branch with a fragment pending and on the tree a promotion leaves: they assert the shipped prefix, never the newest version by name, since the promotion's pull request cannot edit them. The order of patches stays `patches.json`'s, never a comparison of version strings ([[R105]])

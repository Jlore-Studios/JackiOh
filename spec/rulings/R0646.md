Several card patches are built on separate branches at once (issue #63), so branches never edit `patches.json`, the snapshots, `index.json` or `shipped.json`: a branch changes `catalog.json` and adds one pending fragment, `crates/cards/patches/pending/<slug>.json` after its title, holding `{ title, sources, notes, player, cards }` and since [[R1366000]] `plays` and `rule`, where `player` is the player note written by hand ([[R724001]]) and `cards` lists the catalog ids the patch creates, changes or removes; it names no version ([[R1366000]]). `patches check` (run in CI, beside `catalog check`) fails naming the card when a catalog entry differs from the newest shipped snapshot without exactly one fragment claiming it, when a claimed card does not differ, when a fragment claims nothing, or when a fragment's `title`, `sources` or `notes` is empty, since they become the shipped patch's ([[R388]]), or its player note is not one players can read ([[R724001]]); an entry differs when its bytes do, key order included; the catalog with every pending-claimed entry reverted to the newest shipped snapshot equals that snapshot. `patches ship` (idempotent, needs full history) promotes every fragment on `main` in the order of the first-parent commit that added it: it appends the patch — named from its tier after the then-newest version ([[R1366000]]), or with the next letter when that name already shipped, since a shipped version never reopens — dated by that commit's UTC day, with `title`, `notes`, `sources` and the player note from the fragment, snapshots the patch before it with the cards the fragment claims as `catalog.json` holds them ([[R1280000]]; so a later patch's snapshot includes the earlier ones' changes, its card-by-card changes list only its own cards, and the newest snapshot is `catalog.json`), records `{ version, commit, blob }` in `shipped.json`, deletes the fragment, regenerates the derived files and bumps the catalog version to the newest patch; with no fragments it changes nothing. It writes nothing unless `patches check` passes, so that the claims cover every change once and each snapshot differs from the patch before it on exactly its fragment's cards; fragments one commit added ship in the order of their files. On a refusal the workflow opens or comments on an issue ([[R1280000]]). `.github/workflows/patches-ship.yml` runs it on every push to `main` touching `pending/` and opens the promotion as a pull request that merges itself once CI passes, closing any older promotion it supersedes. Tests that read the real history hold on a branch with a fragment pending and on the tree a promotion leaves: they assert the shipped prefix, never the newest version by name, since the promotion's pull request cannot edit them. The order of patches stays `patches.json`'s, never a comparison of version strings ([[R105]])

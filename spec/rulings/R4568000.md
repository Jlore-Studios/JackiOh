Back from the deck editor goes to the Decks tab ([[R3734000]]), but the tab read once, when it mounted:
its kept read returns the kept answer and sends nothing while that answer is under `READ_CACHE_FRESH_MS`
old ([[R3206000]]), and the editor's own read on the way in is the same kept read, so it refreshes
nothing. A player who opened a deck from the tab and deleted or saved it within the window always came
back to the list from before the change: the fold of the landed write (`syncDecks` folding each save
and deletion into the kept decks, `net/api.ts`) landed in memory, and the tab kept drawing the old
list until it was mounted again. A screen drawing the kept deck list now redraws as soon as this
device's own deck write folds into it.

**The listeners.** The read cache holds one listener set per kept path (`subscribeKept` in
`net/readCache.ts`). Everything that changes that path's answer calls its listeners once, after the
change: `keepRead`, `rememberRead`, `updateCachedRead` and `forgetRead`; `clearReadCache` calls every
path's listeners. `expireRead` changes no answer and calls none, and a change to another path never
reaches a path's listeners. A listener that has unsubscribed is never called again. A forgotten answer
leaves what is drawn alone: the hook ignores an answer that is no longer there, and the next read
fills it as today.

**The tab.** The collection's panel read (`useRead` in `routes/collection.tsx`) takes an optional path
to follow, and only the Decks tab's decks read follows one (`keptPaths.decks`). While mounted, the
hook subscribes; when that path's kept answer changes and is not undefined, the hook draws it as its
ready value. A screen showing the tab when the deletion or the save lands therefore drops the deleted
deck's tile, or flips a completed deck's tile to ready with its full count, with no remount and no new
read. The Cards and Progress tabs follow nothing and behave as they do now, and so do the loading and
error states.

Presentation only (CLAUDE.md rule 7): the kept answer stays the server's, and the cost is that the
deleted tile shows for one round trip before it goes.

Decisions the issue did not settle, and what each rejected:

- Per-path listeners, not one listener for every path. With one listener, the wallet panel's answer
  (`keptWallet`, built from three paths) is a new object on every look and would redraw on every
  write.
- Redraw from the kept answer, not re-run the read. Outside the window, a re-read sends a `GET` for
  each mounted panel on every write.
- Wait for the server, not fold the deletion in when the hold sends it. The server decides every
  deletion, and a refused one comes back in its words ([[R2119000]]), so the kept answer stays the
  server's.

Hearthstone semantics do not reach a client cache; this follows the issue's own write folding, drawn
as soon as it lands.

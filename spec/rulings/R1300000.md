A dev account ([[§14.10]]) is one whose profile id the server's `DEV_PROFILE_IDS` lists:
comma-separated profile ids, read at boot with the rest of the environment, each kept in its
canonical form (a UUID in lower case with hyphens, whatever case or form it was written in), blank
entries skipped. One malformed entry fails the boot with a message naming every entry that is no
UUID; unset or blank lists none. The server logs how many it lists, never which: a profile id is
what the account page shows as the account secret ID, hidden until asked for, to every signed-in
account, so a new developer can be listed.

The server decides: `GET /api/auth/me` carries `isDev`, and each dev route checks the list itself
and answers anyone it does not name 403 `forbidden`, writing nothing, before it reads the request's
body. The client shows the Dev tools panel on `/account` when `isDev` is true, and decides nothing
else. Every route acts on the caller's own account, takes no profile id, and is one transaction:

- `POST /api/dev/xp` `{ setId, xp }` gives a positive whole number of XP to the track of a set that
  ships, through the level curve ([[§14.7]]); the level stops at `SET_TRACK_LEVELS` however much XP
  the track holds, and a gift of XP never lowers it. No level's rewards are paid: the reward tables
  are the tracks' sub-issue's, and a level reached here is one whose rewards are owed.
- `POST /api/dev/jlore` `{ jlore }` gives a positive whole number of Jlore ([[§14.1]]).
- `POST /api/dev/fill` brings every collectable card (non-token, unbanned, of a set that ships) to
  `MAX_COPIES`, and owns every cosmetic of the registry but each kind's default, which every account
  owns with no row ([[§14.2]]): a per-card kind (a foil, a finish, a border) on each of those cards,
  a full art on the card it names ([[R1313000]]), an account kind once. What is owned already is
  left as it is, so a second fill writes nothing.
- `POST /api/dev/clear/:part` clears `cards` (every card owned to 0), `cosmetics` (every cosmetic
  owned, on a card or on the account), `jlore` (the wallet to 0), `counters` (every pity counter and
  bar, the cosmetic token cycle and the Chase Shard bar to 0) or `tracks` (every track back to its
  first level, no XP, nothing paid), each apart, or `everything`, all five in one transaction. A part
  it does not know is 404. Packs, tokens and quests are no part of any clear.

Every row a dev tool writes is a ledger row marked `dev` with the reason `dev` ([[§14.11]]): in the
economy's ledgers their own `dev` reason, and in the collection's `collection_grants` the new reason
`dev` (migration 0046), which `collection_grants_dev_check` writes only marked, as each economy
ledger's own check does. A clear is an offsetting row per holding, never a deleted one; a collection
row cleared stays at 0, and `GET /api/collection` sends only the cards owned. The launch grant on
activation ([[R111]]) was untouched: until the economy went live a dev account owned every card
like anyone until it cleared them, and since then it owns the starter cards like anyone
([[R1310000]]) until its fill brings the rest. In end-to-end mode the fixture `e2e-econ` is a dev
account too ([[R1310004]]), and a dev account can also fill a token bar ([[R1310003]]).

Rejected: writing a dev account's card grants under the reason `admin` with the `dev` mark, since a
row's reason is why it was written and an operator's fix is not a dev tool's; and clearing packs,
tokens and quests too, which §14.10 does not name (its quest tools wait for the quests' sub-issue).

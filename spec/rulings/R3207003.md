A gated screen read `GET /api/auth/me` through its gate, and `/decks` read it again through its own `useAccount`, `/play` through the `getMe` of its pairing watch's mount read, and the friends panel through its own read when it opened. `/invite` already took the gate's answer ([[§9.4]]). [[R3206000]] made the second read free inside `READ_CACHE_FRESH_MS`, for the screens that go through `useAccount`; this makes it unnecessary.

**The rule.** The gate hands the account it read to `/decks` and `/play` as it does to `/invite`. `/decks` builds its screen on it and calls no `useAccount`; a `/decks` rendered without one (a test, a host with no gate) reads as before. `/play` starts its pairing watch from it: the mount read, which exists so a reload after a pairing cannot strand the player, is not sent when the handed answer is fresh (`isFreshAccount` in `net/gate.ts`: the answer this tab holds for its session, inside `READ_CACHE_FRESH_MS`) and names no game. A gate may open on a kept answer of any age ([[R2630000]]) and read again behind it, so an answer that is older, or one the tab does not hold, is read again too. When it names a game (a match, a series), the watch reads again before it navigates, since a kept answer may be up to `READ_CACHE_FRESH_MS` old and the game may have ended since (a quick concede and Back to lobby would otherwise be sent back into it); a read that says the game is over leaves the player in the lobby. Only the first run of the watch takes the handed answer; every later run (the wait starting or ending) reads for itself. The wait's own reads, every `SERIES_POLL_SECONDS` ([[R897000]]), are not changed.

**The friends panel.** It opens on the account the page last kept (`keptAccount()` in `net/gate.ts`: the answer this tab's gates and menus left for the session, of any age), and sends no `/api/auth/me` read, for an answer that names no game. An answer that names a game is read again, since Challenge is off while the player is in a game and must not stay off after it ended. A stale "in no game" only enables Challenge, which the server still refuses for a player who is in one (CLAUDE.md rule 7). With nothing kept (before the first read, after sign-out or after `announceAccountChange()`) the panel reads as before.

**Presentation only.** CLAUDE.md rule 7: the account is the server's answer about the signed-in player; the client reuses it. The server still enforces every gate, a ban, a changed account and a refused session arriving on the next request that needs them. Nothing hidden is read or kept.

Hearthstone semantics: the game does not ask who you are twice at one door.

Rejected: trusting a game-naming answer (R3206000 lets one stand for 45 s, long enough to send a player back into a match that has ended); reading the friends panel through the 45 s window of [[R3206000]] alone (an older kept answer would send a read per opening, which is the read this removes, in the common case where the page has been open a minute); a React context for the account (one more owner for a value the gate already owns, and `/invite` already takes it as a prop).

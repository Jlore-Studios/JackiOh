id: R3209000
title: Requests that arrive together share one provider check, and a silence about a session is remembered briefly
cards: "§9.2, §9.4, R159, R194, R1144000, issue #3209"
proven_in:
  - crates/server/tests/api/auth.rs
---
[[R194]]'s session check is one provider call per session of one user at a time, and [[R159]]'s admin lookup one per user id: a request that arrives while that call is out awaits its answer instead of making its own, so a screen's first reads, which arrive together, cost the provider one question. A request that hangs up while its call is out hands the call to one still waiting, and nothing is kept by the sharing itself: once the call lands, a later request reads what the check remembered, or asks again.

A session check nobody answers (a timeout, a 5xx, a 429) is remembered for that session for `AUTH_SESSION_OUTAGE_CACHE_SECONDS`, never longer than `AUTH_SESSION_LIVE_CACHE_SECONDS`. Inside it a request answers at once as it would after the wait: the identity stands, and the email counts as [[R159]] says. Past it the provider is asked again, so a session the provider ended during the outage is refused within R194's live window all the same. An ended answer is never remembered.

The call by token, which the session check makes and tier 3's lookup shares, gives up after `AUTH_SESSION_CHECK_TIMEOUT_SECONDS`, since it sits in front of the request it checks; the sign-in grant ([[R1443]]) and the admin calls keep `AUTH_PROVIDER_TIMEOUT_SECONDS`.

Every answer is kept by user and session, or by user id, so no user's answer serves another's: one session id under two users is two checks.

The published keys are decoded once when their set lands and kept with it, under [[R1144000]]'s rules for when the set is fetched again, so a rotated key verifies once its refetch lands and a key the new set dropped is refused at once.

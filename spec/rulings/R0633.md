An active account keeps its game settings on the server as well as on the device, so a player who signs in on another device, or clears site data, finds them there: one `player_settings` row per profile, holding the settings in groups (the client has four: `gameplay`, `audio`, `fx` and `cards`, one per store of the settings dialog), each `{ at, values }` with the time it last changed on the writing device and a flat object of booleans, numbers and short texts. A player reads only its own row and writes none of it directly (RLS, [[§9.1]]). The server writes it through `GET` and `PUT /api/settings`, which are `active` routes (a pending account has only the code screen, [[§9.4]]) and take the profile from the verified token, never from the body. The body is checked first: at most `PLAYER_SETTINGS_GROUPS_MAX` (8) groups, each a lower-case slug of at most `PLAYER_SETTINGS_NAME_MAX_LENGTH` (40) characters holding at most `PLAYER_SETTINGS_KEYS_MAX` (32) settings named by letters and digits of the same length, each a boolean, a finite number or a text of at most `PLAYER_SETTINGS_TEXT_MAX_LENGTH` (40) characters, and a whole-millisecond time; and the groups an account holds come to at most `PLAYER_SETTINGS_BYTES_MAX` (4096) bytes, a write past either cap answered 409 with nothing written. The server does not know the settings, which are the client's: a group or a setting it is sent is kept, and a client that does not have it ignores it. None of it is a rule: nothing the engine does reads a setting (CLAUDE.md rule 7)

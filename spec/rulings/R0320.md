An active account keeps its tutorial progress on the server as well as on the device ([[R294]]), so a player who signs in on another device finds it there: one `tutorial_progress` row per profile, holding the ids of the lessons it has won and its newest Hide/Show choice ([[R322]]) with the time that choice was made. A player reads only its own row and writes none of it directly (RLS, [[§9.1]]). The server writes it through `GET` and `PUT /api/tutorial`, which are `active` routes (a pending account has only the code screen, [[§9.4]]) and take the profile from the verified token, never from the body. A write merges and never replaces: the stored lessons become the union of the stored and the sent, so a stale device can never remove a completed lesson; and the stored choice is replaced only by one made strictly later, a time after the server's clock counting as now, so a device whose clock runs ahead cannot pin its choice. The body is checked first: at most `TUTORIAL_LESSONS_MAX` (32) distinct lesson ids, each a lower-case slug of at most `TUTORIAL_LESSON_ID_MAX_LENGTH` (40) characters, and a choice that is a boolean with a whole-millisecond time. The server does not know the lessons, which are the client's: an id it is sent is kept, and a client that does not list it ignores it. None of it is a rule: a lesson is still a practice game and records no result ([[R187]]), and nothing the server does reads the row

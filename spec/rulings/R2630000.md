Each gated screen mounts its own gate (`main.tsx`, ONE GATE PER SCREEN), which read `GET /api/auth/me` and held "Checking your account…" until it answered, even when the screen before it had read the same account a moment earlier. A screen now opens at once on the answer this page last read for the same account, and its gate reads again behind it, as a menu does ([[R2125000]]).

**What is kept.** The gate's last answer is kept with the menus' answers (`net/readCache.ts`): in the tab's memory only, by account, emptied on sign-out and on an account switch, as [[R632]] keeps the session. Every answer a gate reads replaces it.

**When a screen opens on it.** Only for an account that is active and owes nothing: no age check or terms ([[R757001]]) and no username prompt ([[R1435]]). A pending account, a banned one and one owing a prompt always wait for the read, so a redirect (to `/invite` or to sign-in), the banned panel and a prompt never rest on a kept answer, and the bounce ONE GATE PER SCREEN was written against (a redemption carried to `/decks` as "pending") cannot come back.

**When it is dropped.** `announceAccountChange()`, which every flow that changes the account calls (an invite's address confirmed, consent, a username, two-step sign-in, a refused redemption), drops it first, so the next screen waits for the account as it now is.

**Behind the screen.** The read behind it settles as any background re-read does: a new answer replaces the kept one, a failed read keeps the screen, and an answer that is not an active account owing nothing redirects or prompts as a first read would. A banned or changed account may therefore see one more screen for a round trip; the server refuses everything it should meanwhile (CLAUDE.md rule 7).

Rejected: keeping it across a reload (`sessionStorage`), left for a later measurement (#2630); and opening on any kept answer, which would bring the bounce back.

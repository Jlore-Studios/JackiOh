Every save of a deck keeps a version of it on the account, so a player who regrets a change can go back to how the deck was. A version is the deck's name and cards as one save wrote them, and when; the deck's portrait and its playmat, backdrop and card back picks are no part of it.

- **What a save keeps.** A save, `PUT /api/decks/:id` or each deck a trio import saves ([[R341]]), whose name and cards are the newest version's keeps none, so a save of the portrait or a pick alone, or a retry ([[R256]]), adds nothing. One within `DECK_VERSION_DEBOUNCE_MS` (60 s) of the newest version's time replaces that version, which takes the save's name, cards and time, so a burst of autosaves ([[R256]]: each `DECK_AUTOSAVE_DEBOUNCE_MS` after a pause) is one version, and the window runs on from each. Any other save adds a version. A deck keeps at most `DECK_VERSIONS_KEPT` (20); one added past them drops the oldest. A deck saved before migration 0065 starts with one version, itself as it was last saved.
- **The History.** `GET /api/decks/:id/versions` lists the caller's deck's versions newest first (by time, then id), each its id, name, cards and `savedAt`. The deck builder's History panel shows each with its date and, against the version before it, the cards put in, the cards taken out and a rename; the newest is the deck as last saved, and the oldest kept has nothing before it to compare.
- **A restore.** `POST /api/decks/:id/versions/:versionId/restore` saves the version's name and cards as the deck's, checked as a save is: the catalog version the client holds ([[§9.4]]), then D1–D5 ([[R250]]), so a version holding a card the catalog no longer lets a deck hold is refused in D3's words. The deck keeps its portrait and picks, which were owned when they were saved ([[R1827000]], [[R1833000]]). A restore adds a version and never replaces the newest however recent, so the version it replaced stays and the restore can itself be undone; only a restore of the name and cards the deck already holds keeps none, as any save of them does. The builder sends the deck's unsaved edit before it asks, and restores nothing over an edit it could not send; a restore that stands ends the builder's Undo and Redo of the deck (#2099), whose steps were taken on the deck it replaced. Its answer updates the decks a revisit opens on, as a save's does ([[R2125000]]).
- **Whose.** The versions are kept with the account, not the device, so they follow the player. Another account's deck is answered as a deck that does not exist, by the list and the restore alike. A client reads its own rows and writes none ([[§9.1]], migration 0065's RLS); the server alone decides what a save keeps. Deleting a deck deletes its versions, and deleting an account deletes its decks and theirs.

Hearthstone keeps no history of a deck, so nothing there decides this; both numbers are the server's, each one constant.

Rejected: a debounce in the client alone, which a second device or a retried save would get around; a version for every save, which an autosave after each pause would fill with one-card steps; restoring through the builder's autosave, whose save the window would merge into the newest version, so the restore could not be undone; making a restore an Undo step, whose undo the autosave would send inside the window and so fold into the restore's version, dropping the restore from the list; and keeping the portrait and picks in a version, which a restore would then have to check for ownership again.

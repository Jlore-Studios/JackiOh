title: "The public card statistics are computed once per patch and kept for their cache TTL (issue #978)"
cards: "§9.11, R654, R807000, R1451"
proven_in:
  - crates/server/tests/api/stats.rs
---
`GET /api/stats/cards` and `GET /api/stats/cards/:id` read every game record of a patch and counted them again on every request, and the drill-down did so for each patch in `patches.json` and the current one: dozens of loads for one card's page, each on the pool the live matches write through. [[§9.11]] already lets a browser keep an answer for `CARD_STATS_CACHE_TTL_SECONDS`; this note has the server keep what it computed for as long.

- **A patch's report is kept for the TTL.** The report of one patch for one `?source=` and one `?pilot=`, with the live-game count the gate reads ([[R654]]), is computed from the patch's records when none was made in the last `CARD_STATS_CACHE_TTL_SECONDS`, and every request in that window reads the kept one. A figure may be as old as the TTL, which the response's `Cache-Control` already allows. The other query filters (`set`, `rarity`, `cost`, `card`) are applied to the kept report, not kept apart.
- **It is computed once.** Requests that miss the same report together wait for one computation. A load that fails is kept for no one: the next request tries again.
- **Both routes read the same reports.** The card drill-down's patch history and its turn and co-played figures read the kept reports of the patches the server ships, so two cards' pages share them. The pilots stay apart ([[R807000]]).
- **How many are kept is bounded** by `CARD_STATS_KEPT_REPORTS` (256), the one kept longest ago dropped first. A patch the server does not ship (neither in `patches.json` nor the current one) is computed on every request and never kept, so a made-up `?patch=` pushes no kept report out. A deploy starts with none.
- **The figures are the same.** For the same records every response is byte for byte what it was ([[R654]], [[R1451]]).

Rejected: aggregating a patch in SQL, or a `statement_timeout` as a backstop, which can follow if the reports still cost too much; keeping the records themselves, which are the cost; keeping a report for any `?patch=` the query names, which lets a script push the real ones out; and dropping the one used longest ago rather than the one kept longest ago, which would reorder the entries on every read for nothing: the TTL already ends every report's life, and the bound only keeps the count down.

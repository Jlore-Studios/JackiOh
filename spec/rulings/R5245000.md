**Why.** On 2026-11-28 `/stats` did not load. Staging's deploy check (run 46096991115) timed out twice at 75 s on `GET /api/stats/cards?mode=all`, which players see as "The card statistics didn't load." Every figure [[R978000]] and [[R3067000]] keep lived `CARD_STATS_CACHE_TTL_SECONDS` (300 s), and once that time was up the next read waited for a whole reload. A reload took over a minute on staging and over five minutes in the owner's account, longer than the client's wait. A match start waited too, since it reads the same figures through `win_rate_snapshot` ([[R3049000]]). A snapshot was also dated from when it was first asked for, not from when its load finished (#5207). So a load longer than 300 s finished already expired, the next read started it again from nothing, and a read made 300 s into a load started a second one beside it, holding both in memory (#5139).

**Kept from when its load finished.** A kept snapshot lasts `CARD_STATS_CACHE_TTL_SECONDS` from when its load finished (`Snapshot::loaded_at`), and every window, history, play versions' table and Hall of Fame cut from it is dated by that time. While a load runs, every read joins it, however long it has run, so only one load runs at a time. A load that fails leaves nothing held, and the next read makes it again, as [[R3067000]] says.

**Stale while it refreshes** (`api::stats::kept_value`). Once a value is held, no read waits on the next one. A read past its time answers at once with the value held and starts one refresh beside it, on a task of its own ([[R5186000]]). Every read meanwhile gets the held value and starts no second refresh. When the refresh lands, later reads get the new value and the held one is let go. A refresh that fails leaves the held value in place, logs `stats.refresh.failed`, and the next read starts another. This holds for every figure cut from the snapshot (its windows, histories, play versions' tables and Hall of Fame bodies), for the drill-down's per-patch reports ([[R978000]]) and for the play rates ([[R1583000]], `PLAY_RATES_REFRESH_SECONDS`).

**One snapshot at a time** (`api::stats::kept_snapshot`). The snapshot itself is not held past its time. The first read past it lets the snapshot go and starts the next one's load. While that loads, every figure already cut from the snapshot let go answers at once. A figure never cut from it waits for the load, as the first read after a boot does. Once the next snapshot is held, each figure answers its last cut while it is cut again from the new one. So the figures shown are at most about one TTL, one load and one cut old. The Hall of Fame is cut from the play versions' table it reads, which can be the one held while the next is cut, so it can trail the table by one refresh. Only a read with nothing held waits: the first after a boot (the bot pool's boot refresh starts that load, [[R3049002]]), or a key past its time by `CARD_STATS_KEPT_IDLE_SECONDS` (an hour) with no read to renew it. Such a key is let go, so a key asked once is not held forever. `CARD_STATS_KEPT_REPORTS` still bounds how many are held.

**The older play versions** ([[R5174000]]). When the snapshot is past its time and a read of the play versions' table or the Hall of Fame comes first, the next snapshot folds them in and serves every read, as the first read's does. A folding load under way when the snapshot is made again is joined, not dropped.

**Memory.** At most one snapshot is held and one loads, never two loads at once. That is no more than before this ruling, when a load longer than the TTL could run twice at once, each holding a whole load (#5139). The figures cut from a snapshot, held while the next loads, are far smaller than it.

`GET /api/stats/loading` still reports a refresh as a load, and `Cache-Control` is unchanged.

Amends [[R978000]] and [[R3067000]] (a read past the TTL answers what is held while it refreshes), [[R1583000]] (the play rates likewise) and [[R5186000]] (a load is joined whatever its age, and the snapshot is kept from when its load finished).

Hearthstone semantics: Hearthstone settles nothing here.

Rejected:
- A longer `CARD_STATS_CACHE_TTL_SECONDS`: every reload would still make the reads at its end wait, a match start among them.
- Refreshing on a timer whether anyone reads or not: on staging's quarter of a processor, a load every five minutes is a constant cost even when nobody is on `/stats`.
- Holding the snapshot past its time to serve every read while the next loads: two snapshots in memory at once, on a server that one load has already killed for memory (#5139; staging's deploy of 5e56c41, run 46098455713, answered a plain 500 after the load).

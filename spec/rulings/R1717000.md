[[§9.8]] asks for an alert on unusual rejection rates, and [[R835000]] gave one only to the match socket: at the API, every request [[R109]]'s limit refused was logged as `api.rate_limited` and counted for nothing, so an account or an address could hammer the API with no alert ever raised. The router now counts each such refusal against the key it was refused on, [[R157]]'s `account:<profile id>` or `address:<ip hash>`, at both places it refuses: the address pre-check before a token is resolved, and the account's or address's own limit. The count is kept over `API_REJECTION_ALERT_WINDOW_MS` (60 s) and crossed strictly over `API_REJECTION_ALERT_THRESHOLD` (20 refusals): the 21st refusal inside the window emits `api.rejections.unusual` through `log_alert`, with the `key`, the count as `rejected` and the `windowMs`, the same shape as `match.rejections.unusual`, so whoever watches alerts watches one kind. A key alerts again only once a whole window has passed since its last alert, so a sustained flood alerts once a window and a trickle never does; a key refused 20 times, or refused over more than one window, raises nothing.

Only the router limit's refusals count. A 401, a 403, a handler's own refusal and the per-route limits ([[§9.4]]'s codes, chat, friends, challenges, replays) count for nothing; each keeps its own log line. A key keeps at most 21 refusals, and a key with none left in the window is swept once a window, so a flood holds bounded state, as `hits` does. The count is in memory, per server, as the limit is.

Rejected: one alert per key for the process's lifetime (the analogue of [[R835000]]'s once per match: a sustained flood would alert once until a restart, and the API has no match to end it), and a store-backed cross-process score (it needs a migration). The alert has its own constants, with the same values as the socket's, so tuning the API's does not tune a seat's.

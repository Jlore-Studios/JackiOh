Card patches are tracked, back to the first catalog: `packages/cards/patches/patches.json` lists every patch in order (version, date, title, source, notes), each patch's snapshot is the whole catalog as that patch left it, and a generated index maps each card id to the versions in which it changed. The history before this patch is rebuilt from the catalog's git history: v0.1.0 (the first Core catalog, 2026-09-18), v0.1.0b (the Core balance changes of 2026-09-22), v0.1.0c (#95's text and The Coin, 2026-09-24), v0.1.0d (the Radiant pass, [[R275]]–[[R279]], 2026-09-25), v0.1.1 (patch v0.1.1, 2026-09-27) and v0.2.0 (this patch). The catalog version is the latest patch's version wherever it lives — the cards package, the server's env and the client's copy, and the `cards` rows and settings the catalog seed stamps — and a patch bumps it everywhere at once, so every patch reseeds ([[R105]]); patches are ordered by `patches.json`, never by comparing versions. A patch is made by one script that snapshots the catalog, diffs it against the previous snapshot and writes its notes card by card, and a test holds the catalog equal to the latest snapshot and the version equal to its version. An older version can be read: the collection's card detail shows each patch the card changed in, with its faces as they were and the words and numbers that changed marked as [[R277]] marks a Radiant face; a public Patch notes page lists every patch and the cards it touched; the server serves any snapshot (`GET /api/catalog/:version`); and the engine can register an older snapshot, so a match folds under the version it started with. A patch that changes what a script does, not only a number, keeps the old script under `<id>@<version>`, so a match pinned to that version runs the old code. A card's `loc` ([[§5]]) is card data and part of its patch history. Several patches are built at once ([[R646]]): a branch changes the catalog and adds one pending fragment claiming the cards it touches, `patches check` fails unless every catalog change against the newest snapshot is claimed by exactly one fragment, and `patches ship` promotes each fragment in ship order after it merges, snapshots it, records it in `shipped.json` and bumps the version; the catalog then differs from the newest snapshot on exactly the claimed cards, and a test holds the reverted catalog to the snapshot

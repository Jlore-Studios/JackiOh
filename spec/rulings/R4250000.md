**Why.** The server accepts a match or co-op socket first and judges it after (`handle_match_socket`), so every refusal reaches the browser after its open event: 4401, 4403, 4404, 4429, and 1011 for a fault ([[R148]], [[R2478000]]). Both clients reset their reconnect backoff in `onopen`, and 4429 and 1011 are drops on [[R1441]]'s backoff rather than settled refusals ([[R2478000]]). So a spent account reopened at the backoff's first step, about four times a second, until its minute's window drained, and during a server fault every client in a game hammered it at that pace for the whole outage: the stampede [[R1441]]'s jitter exists to prevent.

**The rule.** A match or co-op socket's backoff starts over once that socket has delivered a view, not when it opens. `onopen` still sends `hello` and still shows the connection as open; the reset moves to the first `view` frame, the point `awaitingFirstView` already marks. A socket refused after the upgrade climbs the steps ([[§9.5]], [[§9.8]]), as one that never opened does: a quarter second, half a second, one, two, then every five seconds. Only a delivered `view` resets; any other frame before it changes nothing, since the game has not been delivered. The social socket already works this way, resetting only on its first `social` frame ([[R3214000]]). Quick retries return only once a connection has actually delivered the game.

**Hearthstone semantics.** Hearthstone semantics settle nothing here.

**Rejected.** Adding 4429 to `REFUSAL_CLOSE_CODES`: that would stop retrying for good, when [[R2478000]] wants a retry once the window drains (a refused upgrade is not counted, so the window drains). [[R1115000]]'s 4401 handling is untouched: a renewed token still opens one more socket at once.

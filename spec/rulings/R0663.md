A signed-in player changes their address from the account page (`/account`), straight from the client to the auth provider (`PUT /auth/v1/user` with the new `email`, the session's access token and `redirect_to` `<origin>/login`), with a PKCE challenge under a verifier of its own (`email_change`, [[R323]]). The form checks the address's shape and that it is not the account's own before it sends (the current address read from the session token's claim, for display only), and a token the provider no longer takes is renewed once and the request sent again ([[R194]]). The provider mails a confirmation link to the new address, and to the current one too when the project's secure email change is on; the address changes only once the change is confirmed, so the form says to open the link (or both) and to sign in with the current address until then. Every refusal about the address itself (`email_exists` included) reads as one sentence, because naming an address another account holds would be an account-existence oracle ([[R160]]); a rate limit reads as [[R192]]'s. The link comes back to `/login` like any other: its code is exchanged and the session judged as [[R193]] judges a confirmation, signing nothing in and revoked, and the screen says the new address is confirmed and to sign in with it (an implicit-flow `email_change` link, [[R324]], reads the same). The game's own profile keeps no copy of the address (`public.profiles` has no email column): `/api/auth/me` reads it from the auth provider, so the account shows the new one once it is confirmed

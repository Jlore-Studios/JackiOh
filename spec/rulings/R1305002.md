[[§14.5]] says a card token unlocks any new card ([[§14.3]]) of a set that ships that the
account chooses, and redeeming a token is one transaction:

- **What it buys** is one copy of one card the account owns fewer than `MAX_COPIES` of: the
  catalog must name it, it must be no token, and its set must ship ([[R1420]]). Anything else,
  an unknown id, a token, a card of a set that has not shipped, a card already owned, or no
  card token held, is refused with 409 and spends nothing.
- **The transaction** is the collection's two writes, then one `CardToken` spent, all with the
  same `at`; one commit. A valid redemption grants exactly once: spending the token first is
  what makes the second redemption a refusal, which writes no row.
- **The collection's reason is `craft`.** Migration 0002's `collection_grants_reason_check`
  closes the reasons to `pack | craft | reward | refund | admin | launch`, and a new reason
  takes a migration, which is out of scope here. A token unlocks a chosen card exactly as a
  craft does, so the row says `craft`; the inventory row, whose ledger already holds
  `token_redeem`, still says `token_redeem`, so the redemption reads as one. #1333 may revisit
  the reason when it brings §14's text in line.
- **The lock** is the account's economy lock ([[R1301003]]), so a token spent and a bar paying
  cannot interleave.

Hearthstone semantics: Hearthstone crafts any card for dust; the spec's token unlocks any new
card of a set that ships, and this only fixes what the ledger calls it and what refusals cost.

Rejected: a new collection reason without its migration, which the schema refuses; spending the
token after the commit, which would grant the card but keep the token on a failure between
them; and refusing an unknown card with 400, which would tell a choice apart that spends
nothing either way.

§14's text is #1333's to change.

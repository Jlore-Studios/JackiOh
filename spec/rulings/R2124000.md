The client gives up on a request after `API_REQUEST_TIMEOUT_SECONDS`, and a spend the server finished after that point used to run again when the player pressed again: a second pack bought, a second token spent. So a spend runs once.

**The key.** Every spend takes an optional `Idempotency-Key` header holding a UUID: `POST /api/packs/buy`, `/api/packs/open`, `/api/tokens/redeem-card`, `/api/tokens/redeem-cosmetic`, `/api/cosmetic-packs/open`, `/api/cosmetic-packs/chase` (every spend of the economy) and `/api/codes/redeem` ([[§9.4]]). A header that holds no UUID is 400 `bad_request` and spends nothing. A request without one runs as it always did, so a tab of an older client still works. A key belongs to its account: the same key sent by two accounts is two keys, and neither reads the other's.

**On the server.** Under the account's economy lock ([[R1301003]]), in the spend's own transaction: a key the account sent before with the same route and body answers the status and body it answered then, and spends nothing; a key it sent before with another route or body is 422 `idempotency_key_reused`, and spends nothing; an unknown key runs the spend, and its answer is written in the same transaction as the grant, so the two commit together or not at all. The lookup comes before every check of the spend, since a retry finds the pack, the token or the full bar its first try spent gone. A redemption looks first, before the breaker and [[R145]]'s account checks, since the redemption it replays made the account active; every outcome of a redemption, a replay and the 422 among them, is padded to [[R107]]'s floor. The body is kept only as a keyed hash, under `CODE_PEPPER`'s `:body` domain, so no invite code is kept.

**What is kept.** Only a spend that committed keeps its key: a refusal (a short wallet, no pack held, an exhausted code) writes nothing, so the same key runs again once the refusal no longer holds. A key and its answer are kept `IDEMPOTENCY_KEY_TTL_HOURS`; the retention loop deletes them after that, and an account's deletion takes its keys with it ([[§14.11]]). A key is the server's alone: no client reads or writes one.

**The client.** A press of Buy, Open, Redeem token, Buy chase or Redeem code mints a key (`crypto.randomUUID()`), and that press's retries, "Try again" after a timeout among them, send it again. Any answer from the server, a refusal included, ends the press, and the next press mints another; a press that got no answer (a timeout or a failed transport) or a server error keeps its key, and a press with the same spend and body before an answer is its retry.

**Unchanged.** A deck or trio save is a `PUT` of a client-minted id ([[R256]]) and a match action carries its nonce ([[§9.3]]); both were already safe to send again and take no key. A practice claim burns its seed once ([[R1303001]]) and takes none either.

**Rejected.** Keeping refusals too, which would replay a stale 409 to a retry that would now succeed; one key space for every account, which would let one account's key stand in for another's; keys on the practice claims and the dev routes, which are no spend of the economy's routes; and a required header, which would break every tab of an older client.

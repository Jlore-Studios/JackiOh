**Why.** A card changed several times shows up on Versions as several rows that only their spans tell apart (Profe Yates: v0.6.0 – v0.6.6h, then v0.6.7g – v0.6.7k). The owner asked for a column that numbers them as a person would talk about them, "the third version of Profe Yates": v1 at launch, then v2, v3, and a letter after the number, as a micro's (`docs/issues-and-patches.md`, Version numbers), where only the play changed and no text did (issue #5035).

**The count.** A card's play versions ([[R4675000]]), oldest first, are numbered over its whole shipped history by `jackioh_cards::play_versions_of`, which already reads each version's change lines and claims:
- Its first play version is `v1` (`FIRST_ITERATION`), whatever the line that adds it shows.
- A later one takes the next number, its letters starting over, when the version it starts at has a change line on the card itself that changes a field the face shows: `FACE_FIELDS`, beside `WORDING_FIELDS` and `PLAY_VERSION_QUIET_FIELDS` in `crates/cards/src/patch_history.rs`, today `name`, `cost`, `type`, `rarity`, `base.text`, `radiant.text`, `base.attack`, `base.health`, `radiant.attack`, `radiant.health`, `base.keywords`, `radiant.keywords`, `base.xStats` and `radiant.xStats`.
- Any other takes its number's next letters, counted as a micro's are ([[R3631000]], the one `next_letters` the version names use): b to z, then aa, ab. That is a play version started by a `plays` claim alone (a script change claimed through `--plays`, a token's change restarting its card, a rule claimed for its family, [[R1365000]]) or by a line that changes only fields the face does not show (`params`, `tags`, `dealsDamage`, `snapshotOf`, `resource`, `usesPlague`, `grants`).
- So a card's iterations read v1, v1b, v1c, v2, v2b, v3: unique, and in its play versions' order.
- The line must be on the card: a token restarted by its card's change takes a letter, since nothing on the token's face moved.
- Wording alone starts no play version ([[R4675000]]), so it starts no iteration. A wording line in a version that starts one by a claim or another field does move the number: the face changed where the play version began.

The numbering is the card's own and never moves. It is counted over the whole history, so a play version wholly before the game records began (about v0.3), which has no figures, still counts. A filter, the match type, the pilot, Past versions only, or the Major patch running cut ([[R5040000]], which keeps each cut row's play version whole but for its span) only changes which rows show, never their numbers. No version string is parsed ([[R105]]): the count reads the history's order and its lines, and the client prints the label it is sent. As this was built, the 4,052 play versions of the 800 deck cards held 1,576 numbers and 2,476 letters; every card began at `v1`, and xxFreshJack, restarted 32 times with its face unchanged, ran from `v1` to `v1ag`.

**The route.** Each row of `GET /api/stats/versions`, and so each Hall of Fame entry's rows, sends `iteration`, the label (`"v1"`, `"v1b"`, `"v2"`: `ITERATION_MARK`, the number and the letters, `PlayVersion::iteration_label`), carried by `PlayVersionFigures` ([[R4675001]]). The client restates no field list and counts nothing (CLAUDE.md rules 7 and 9): it prints the label as sent.

**The column.** "Iteration", right of Since, wherever a row of the Experimental tab's running views (Major patch running and Historical, [[R4678001]]) or Versions ([[R4680000]]) shows Since: the table's column and the grid's figures. Running prints its live play version's iteration, Versions each row's own. Its header's tooltip says what a number and a letter mean; no note on the page ([[R4155000]]). A row from a server deployed before this field prints "—". The column is no sort key: within a card the iterations already run in its play versions' order, across cards a number orders nothing, and a sort by when each play version began is issue #5033's.

Rejected:
- Sending the number and the letters apart (`iteration: 2`, `iterationLetter: "b"`): the client would only join them, and the label is what every reader prints.
- Counting on the client from the rows: it would restate `FACE_FIELDS` (CLAUDE.md rule 9) and could not see a change line or a claim.
- Numbering only the rows shown, or only the play versions with records: a filter or the records' start would renumber a card's versions.
- `grants` as a face field: the issue's list leaves it out, and the history's two `grants` lines (Permanent Underclassman and Upperclassman, v0.3.2) each change the text beside it, so the count is the same either way.
- An `added` line as a face change: a card's first play version is `v1`, and no card in the history is added twice.

Hearthstone has no counterpart.

[[§14.9]] reads a quest's goal from a finished game's public events, and the pool gains two goals the
spec did not define, `positionSwitches` and `radiantUpgrades`, besides a quest for the Stinkyscape
set, which shipped without one, and for Training Grounds, which shipped ([[R2204000]]) while this
change was open and arrived without one the same way. The spec says neither what counts for the two goals nor that a set
that ships has a quest, so:

- **A switch and an upgrade count as the record counts them.** A `positionSwitches` quest moves by
  the seat's `positionSwitches` and a `radiantUpgrades` quest by its `radiantUpgrades`, the counts
  [[R1256000]] reads off the game's events: a switch by a Unit the seat controlled and a card of the
  seat's that an effect made Radiant, whoever's effect it was, as a `fireTraps` quest counts the
  seat's Traps that fired whoever fired them. A card created Radiant is no upgrade. A record without
  the counts (written before [[R1256000]]), a game the server could not read, and a co-op game, whose
  quests read its result and attacks alone ([[R1502000]]), move neither. The game moves them as it
  moves every quest held when it ended ([[R1304001]]).
- **Every set that ships keeps a set quest.** The pool holds at least one `playSetCards` quest for
  each set `SHIPPED_SETS` lists ([[R1420]]), so the change that ships a set adds its quest. A unit
  test of the shipped pool holds it.

Hearthstone semantics: Hearthstone's daily quests count what the player's cards did in a game, and
its pool asks for games with each class, so no class a player can pick is left without one.

Rejected: counting only the switches and upgrades the seat's own actions caused, which the record
does not keep and the hook would have to fold the log again for; and checking the set quests in
`quests::problems`, which checks any list of entries (its tests pass one or two) and runs when the
server first reads the pool, so a gap would fail the running server instead of the build's tests.

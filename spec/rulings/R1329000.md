[[R1266000]] gave each carried version the win-rate table it shipped with by reading the table's
`patch` label: the build's table for that version and every later one, the empty table before it.
That held while one table had ever been filled. The next refresh would replace the build's table,
and with it the table every version from the last refresh on was played with, unless someone kept
the old one by hand; and nothing held the table to a card patch ([[R1101]]), since no fragment
claimed it. So each shipped version keeps its own table, as a file, with the patch that ships it.

**The claim.** A pending fragment claims the table with `winRates: true`, and `cargo jackioh patches
<version> …` sets it when the rows of `crates/cards/data/win_rates.json` differ from the newest
shipped version's and no other pending fragment claims them. `patches check` fails when the rows
differ and no fragment claims the table, when two fragments claim it, and when one claims it and the
rows do not differ. A fragment may claim the table and no card: the table is part of what a patch
ships. Tables compare by their rows (`cards`), which is all a fold reads; `patch` and `source` are
labels.

**The files.** `patches ship` writes `crates/cards/patches/win_rates/<version>.json` for every version
it ships: the working table for the fragment that claims it and every version after it, the patch
before it's for every version before it. Its proof extends to the table: a claimant's rows differ
from the patch before it's, and the last version's are the working file's, or nothing is written.
`shipped.json` records each table file's git blob (`winRatesBlob`) beside its snapshot's, so a
rewritten table fails as a rewritten snapshot does. The folder is beside the snapshots, not among
them, so no reader of `patches/*.json` sees a table. A version with no file has the empty table,
which every version before v0.3.15 shipped with. v0.3.8 to v0.3.16 (#1341) and v0.3.17 (#1293)
shipped before this ruling landed, by a `ship` that wrote no table; v0.3.15, v0.3.16 and v0.3.17
shipped with the filled table, as [[R1266000]]'s first reading gave it them, so issue #1329 wrote
their three files, that table, with their blobs in `shipped.json`, and the versions before them keep
no file.

**The fold.** `crates/cards/build.rs` puts each carried version's table into `history.json`,
identical tables once, and that version's shipped catalog carries it (`with_win_rates`), so
[[R1266000]]'s fold reads it; the browser's module carries the tables of the versions it carries.
`patches check` fails a carried version whose table's rows are not its file's, or that has rows and no
file.

Rejected: the issue asked that `ship` take the table as the fragment's adding commit left it, as
`ship` then took `catalog.json`. [[R1280000]] has since built each snapshot from its claims as the
working tree holds them, so that a fragment edited after its merge never wedges the queue, and the
table follows it: the claiming fragment ships the working table. v0.3.15's fragment was added before
issue #1266 filled the table, so its adding commit holds the empty table, and the adding-commit rule
would have shipped v0.3.15 without the rows it shipped with.

**Code blocks stay the build's.** Meditative+ #25 KY's Intuition's code blocks ([[R1183004]]) are cut
from each card's script source, so they change with any script edit, card patch or not, and a
version has no well-defined set of them. They cannot make a replay refuse. A code Discover's labels
([[R1183005]]) live in its open prompt alone, and both its answer and the end of the game
([[R216]]) clear `state.pending`, so they never reach a 1v1 final hash; a Duos replay is held to the
result it recorded, not to a hash. The pool it offers from is the same on every build: a card a
carried version holds is in `catalog.json` with a script, and `build.rs` cuts a block for every
non-token card there. Two things do change. A replay's step, or a rebuilt live prompt, shows today's
code rather than the code the player saw; and a practice save taken with a code Discover open does
not resume on a build whose blocks for the offered cards differ, since resuming checks the save's
hash, as any change to a script's behaviour already stops such a save resuming.

**Tables added later.** A compiled table the engine reads while it folds answers from the shipped
catalog the fold runs under first (`catalog::folding()`), as the definitions, the scripts, the catalog
version and the win-rate table do, or a ruling says why it does not, as this one does for the code
blocks (`crates/engine/src/catalog.rs`'s header).

Rejected: recording each lookup's answer per game, so that tables could change freely. A replay keeps
its inputs and its final hash and refolds from the seed, so an answer kept in the state is only ever
compared, never read back; to be read back it would have to become an input every recorder stores and
every fold feeds in (the match log, Duos, practice saves, the golden traces, the browser's module and
the tools); it covers lookups only, while definitions and scripts already change and are versioned
([[R767000]]); and every game already records its catalog version, which [[R1101]] makes the table a
function of. Should the table ever refresh between card patches, a setup field naming it, as
`ReplayInput` names handicaps and last boards, beats a record per lookup.

Nothing of it is in `GameState`, and no hash moves: every carried version keeps the table
[[R1266000]]'s first reading gave it, the filled one for v0.3.15 and the empty one for every version
before it.

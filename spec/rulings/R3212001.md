**Why.** The workshop's autosave ([[R256]]) sent one `PUT` per dirty deck and trio and one `DELETE` per
deletion, one after another, so a pass over several edits cost as many round trips. Tracker #3203 asks
for less compute and faster traffic.

**The route.** `POST /api/decks/sync` takes `{ decks, trios, deletedTrios, deletedDecks }`: each deck
and trio its `PUT`'s body with its `id`, each deletion an id; a list may be absent. More than
`DECK_SYNC_ITEMS_MAX` items in all, or a list that is not one, is 400 and runs none of it. The server
runs every deck save, then every trio save (so a trio may name a deck saved earlier in the request),
then every trio deletion, then every deck deletion, each exactly as its own route runs it, with the
same checks ([[R250]], [[R252]]), in its own transaction, so each is as idempotent as its `PUT` or
`DELETE` and a retry of the whole request saves nothing twice. It is no spend: no turn, no key.

**A refused item refuses alone.** The answer holds one entry per item, in the request's order:
`{ id, deck }`, `{ id, trio }` or `{ id, deleted }`, what its own route answers, or `{ id, status, error }`
with the status and error body its own route would have answered. The rest of the request still saves.
A fault of the server's on any item fails the whole request with that error; what saved before it is
saved, and the retry saves it again as the same deck.

**The client.** A pass sends every unsaved deck and trio and every deletion whose undo hold has ended
([[R2119000]]) in one request, at most `DECK_SYNC_ITEMS_MAX` items, the rest in the next pass, with
`keepalive` when the page is going away. Each item's outcome is handled as its own request's answer was:
a refused deck or trio is marked in the server's words, a trio naming a deck not saved yet waits for it,
a refused deletion comes back. A request that fails, or that the server refuses whole (a server older
than the route answers 404), judged no item: the pass stops and tries again later, as after a lost
connection. The single routes stay for tabs of an older client.

Hearthstone semantics: a deck saves alone, and one deck that cannot save keeps no other from saving.

Rejected: all or nothing, which would let one bad draft keep every other edit from saving; one
transaction for the whole request, since a refusal raised by the store aborts every write in a Postgres
transaction; and an idempotency key for the request, since every item is idempotent by its own id.

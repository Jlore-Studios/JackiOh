title: "A game record the fold cannot read is set aside uncounted, its detail emptied, with an alert (issue #1715; amends R1044000 and R1044001)"
cards: "§9.11, R1044000, R1044001"
proven_in:

  - crates/server/tests/api/game_records.rs
---
[[R1044000]]'s fold of the records written before the totals read a batch and parsed every record in it before marking any folded, so one record whose detail did not read (a row in an older format, or drift between two deploys) failed the whole batch. The next pass met the same record at the head of the queue and failed again, so nothing behind it was ever counted, and the retention loop only logged `game_records.fold_failed` each hour. `stats-export`, which reads the records, failed on the same row.

Now the fold reads each record on its own. A record whose detail does not read is set aside: marked folded, counted in no total, and its detail emptied at once, as [[R1044001]]'s purge would empty it a week on. Its id stays, so a second write of the same game is still refused, no read of the records meets it and no fold takes it again. `game_records.fold_poison` names its id and why its detail did not read, once its batch has committed, and `jackioh-server stats-fold` prints the same. The rest of the batch folds, and the batch's size counts the record set aside, so the loop goes on while a batch is full.

This amends [[R1044000]], whose fold counted every record it took: such a record has no counts to fold. It amends [[R1044001]], under which a record kept its detail a week once folded: this one loses it at once, since it can never be read, and only an unfolded record is ever set aside, which no record written since migration 0041 is.

Rejected: a quarantine column, which needs a migration for a row nothing can read; keeping the detail, which leaves the reads of the records failing on it until the purge, or has them skip an unreadable row silently; and trying it again each pass, which is the wedge this ruling ends.

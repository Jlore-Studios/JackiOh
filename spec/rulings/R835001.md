title: "Queued hellos coalesce per socket generation (issue #835)"
cards: "§9.5, §9.8, R109, R137"
proven_in:
  - crates/server/tests/actor/match_actor.rs
---
A `hello` asks for [[§9.5]]'s fresh full view, and reconnect is idempotent — asking twice changes nothing — so a `hello` that arrives while one for the same seat is still queued is absorbed by it instead of queueing another `view_for` plus `legal_actions`, the most expensive reply the actor produces. A hello flood therefore costs at most one outstanding view push per seat, and the task queue stays bounded, under the same per-seat scope as [[R137]].

The pending flag is keyed to the socket generation, which every `attach` bumps (the first included): a `hello` from a newer socket always enqueues, even while the older socket's Hello is still queued, and a run clears the flag only for its own generation. A Hello that already ran answers nothing twice — a later hello is a new request — and what each pushed view carries is unchanged, still that seat's own view with its own legal array under one lock.

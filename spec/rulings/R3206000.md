Tracker #3201 asks for less compute and faster traffic, and a menu kept its last answer ([[R2125000]]) only to draw it sooner: every screen still read again behind it, and so did the gate ([[R2630000]]), the wallet and the landing, on every move between screens. The kept answer now carries the time its read finished, and a young one saves the request. Reads in flight are shared as well.

**The window.** `READ_CACHE_FRESH_MS` (`net/readCache.ts`, the client's own number) is 45 seconds, midway in the 30 to 60 the issue allowed. A kept answer younger than it is *fresh*: a kept read (`keptGet` in `net/api.ts`) returns it and sends nothing. An older one behaves as [[R2125000]] has it: a screen draws it at once and reads again behind it, and a failed read keeps it. One window serves every kept path; the statistics table and the friends list keep what [[R2125000]] says (the table's read is a kept read and is fresh like the rest, the friends list is read on its own poll and is never used in place of one). An answer is as old as the read that made it: a fold of a write's answer into it (a bought pack's counts, a saved deck) keeps the age it found and never makes it fresher, while a write's own answer replaces the entry and is as fresh as the server's last word. A clock set back leaves nothing fresh.

**Sharing.** A `GET` of one path, query included, with one token, asked while one is out, waits on that one's answer (`apiRequest`, `sharedGet`). It is shared by every caller, kept or not (the news, the gate's `/api/auth/me`); never a `POST`, `PUT` or `DELETE`, nor a `GET` that sends a body, a `keepalive` or an `Idempotency-Key`; never across tokens, a renewed token being another token for this (the kept answer is by account, a read in flight by token). The shared request runs on its own `AbortController`: one caller's abort rejects that caller alone, with `ApiUnreachableError` as before, and the request is aborted only when the last caller waiting has left; a caller whose signal is already aborted sends nothing.

**Writes move the epoch.** `readCache.ts` counts the writes (`writeEpoch`): every spend (the one request that sends an `Idempotency-Key`, [[R2124000]]) when it settles, answer or refusal, since one that failed may still have run, and every `rememberRead`, fold, `forgetRead` and `clearReadCache`; a finished read (`keepRead`, the gate's and the friends poll's) does not, and neither does a write that changes no kept read (the presence heartbeat the landing sends as it mounts would otherwise keep any read beside it from being kept). A read asked after the count moved never joins one sent before it, and a kept read that finished after it moved is not kept: it may show what the write changed, and the write's own entry stands. A read that lands after sign-out is therefore not kept either.

**What a write drops.** A spend or write whose answer does not carry a kept read drops it (`forgetRead`, as the news claims already did): a pack opening drops the collection, the owned cosmetics, the tokens and the cosmetic packs (its answer folds into the packs); a card token the collection; a cosmetic token the owned cosmetics; a cosmetic pack opening the collection, the owned cosmetics and the tokens; a chase the collection and the owned cosmetics. A game's paid result (`announceWallet()` with no balance, which the match, the practice board and the co-op board announce) drops the wallet, the quests, the tracks, the packs, the tokens and both ladders' boards (`forgetPaidReads`): what its Jlore, XP, level or quest payout and the ladder move changed, which no answer carries. A dev tool that succeeds empties everything kept. A quest falling due, and a quest read the player asks for again, expire the quests' answer (`expireRead`: shown as before, never fresh) so the read reaches the server.

**The gate.** A gate whose kept `/api/auth/me` answer is fresh, for an active account that owes nothing, sends no read: the screen opens on it ([[R2630000]]) and stays. A pending, banned or owing account is always read, and so is any account after `announceAccountChange()`. The session read, the renewal before expiry (`useRenewalBeforeExpiry`) and the 401 path are as they were, and a gate that opened on the kept answer does not keep it again, so the window closes. The server still enforces every gate (CLAUDE.md rule 7): a ban, a changed account or a refused session reaches this screen on the next request that needs it, or when the window ends.

**The wallet.** The pill reads through the same window: a navigation, or the page coming back into view, inside it of the last answer sends no wallet read. A paid result reads at once, as above.

**Never.** The window never covers a match's, a series', a duos room's, a watch's or a replay's reads, which are not kept ([[R2125000]]); the news and the friends list are outside it (a claim changes the news, and the friends poll is the way they stay current).

Presentation only (CLAUDE.md rule 7): every answer is the server's, about this account alone, kept in the tab's memory, emptied on sign-out; a screen may show what the server changed elsewhere for up to the window, and the server refuses whatever that stale view asks for. No hidden information is read or kept.

Hearthstone semantics: a shop shows what it just read, and reads again only when it has been a while.

Rejected: a window per path (one number to hold and explain; the paths that change faster are dropped by the writes that change them); `localStorage`, which outlives the tab and a sign-out; keeping the news or the friends list in the window; a window that a fold or a gate mount makes fresh again (the answer would never age while the player moves around); sharing only inside `keptGet` (the gate's and the news' reads are shared too); an epoch for each path (the account's and the friends' answers are kept all the time and would keep cancelling the reads beside them); counting every write that settles (the landing's presence heartbeat settles beside its first reads and kept them from being kept).

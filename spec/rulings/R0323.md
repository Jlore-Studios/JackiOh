The implicit flow put a session's tokens in the link's URL fragment, where history, a shared screen or a referrer could read them. So the mailers (the sign-up's confirmation, its resend, the password reset, and since [[R663]] the email change) send a `code_challenge`, the SHA-256 of a random verifier in base64url, with `code_challenge_method` `s256`, and keep the verifier in the browser's `localStorage` inside try/catch, one per kind of link; a resend reuses the sign-up's verifier, so the first email's link keeps working. The link comes back to `/login?code=…`, or to the Site URL `/`, which moves it to `/login`. The code is read on those two paths only, is scrubbed from the address bar before anything renders, and is exchanged at `/auth/v1/token?grant_type=pkce` with `auth_code` and `code_verifier`, newest verifier first; one the provider answers `bad_code_verifier` belongs to another link and the next is tried. The session that comes back is judged exactly as [[R193]] judges a link's session: a confirmation signs nothing in and is revoked, and a recovery is held only for the reset this browser asked for (or once the player types its address). No token is ever in a URL, so nothing in history needs spending

Beside the password form, a player may ask for a sign-in email: it holds a link and a one-time code, and either signs in. It is sent only to an account that exists and has confirmed its address (`create_user: false`). Sign-up stays with the password form, and an unconfirmed account cannot be signed into this way, since the provider treats it as not signed up yet and a link would confirm an address someone else registered first while their password stayed on it ([[R193]]). The request answers the same neutral sentence whatever the provider said, an unknown or unconfirmed address included, and waits out the provider's per-address interval, as the other mailers do ([[R192]]). A wrong, spent or expired code and an address with no account read as one sentence ([[R160]]). The link carries a PKCE challenge whose verifier only the asking browser keeps ([[R323]]), so its code exchanges only there, and that session is kept: this is the one link whose session signs in, because it can finish only where it began, while [[R193]]'s links can be sent to anyone. A sign-in link opened in another browser exchanges nothing there and reads as [[R324]]'s link from elsewhere; the code in the same email works anywhere. An implicit-flow link of type `magiclink` signs nothing in ([[R193]]). Either way the account then passes the gate exactly as after a password sign-in ([[§9.4]]): its profile is whatever it was, `pending` until a code is redeemed

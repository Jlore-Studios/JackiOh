[[R109]]'s limit of `API_REQUESTS_PER_MINUTE` (300) a minute per account was checked after the router had resolved the caller, and resolving the caller opens a transaction and reads the profile. A request past the limit was refused with [[R192]]'s 429, but only after it had checked a connection out of the pool (ten of them, shared with the match actors' log writes), so one signed-in client stuck in a loop kept every connection busy and everyone else's requests, live matches' saves among them, waited on it. A match, co-op or watch socket's upgrade verified the token and read the profile too, and no limit counted it: `WS_MAX_CONNECTIONS_PER_ADDRESS` caps the sockets open at once, not how often they reopen.

The server now keeps, per `App`, a bounded in-memory map from each verified auth user to the profile id it last resolved to (`api::http::KnownProfiles`). It holds at most `KNOWN_PROFILES_MAX` (10,000) users, and a new user past the bound drops the one remembered longest ago, which then reads the store once more. `resolve_caller` fills it from every profile it reads or creates. Once a token verifies, the user is looked up there: if the map knows the profile and that account's bucket is spent (`retry_after_ms(account_key(..)) > 0`), the request is refused at once with [[R192]]'s 429, before `db.begin`, logged as `api.rate_limited` and counted toward [[R1717000]]'s alert as every refusal of the limit is. The key stays `account:<profile id>`, never the user id or the token, so two tokens of one account still share one bucket ([[R157]]).

The map only refuses early, and never grants anything. It holds an id and nothing else, and a request it lets by still reads the profile, counts against the bucket the profile's id names and meets [[§9.4]]'s gate, so a ban or a pending account is judged on the store's word and a stale entry can at worst refuse early an account that is already over its limit. A user the map does not know reads the store as before, so a new account is still created lazily ([[§9.4]]), and a server that has just restarted learns an account from its first request. The look is not a count: a refused request is not recorded, as [[R109]] says, so the window drains.

A match, co-op or watch socket's upgrade whose token verifies is counted as one request against the same account bucket (`api::http::upgrade_profile`, which `/ws/match`, `/ws/duos` and `/ws/watch` share). A known account whose budget is spent is refused before the store is read; otherwise the profile is read (a socket never creates one), remembered, and the upgrade counted. The refusal is the one `error` frame with code `forbidden`, as every refusal of [[R148]], with the message "too many requests; slow down", and a close with 4429, a private-use mirror of 429 beside 4401, 4403 and 4404. A token that does not verify costs the store nothing and counts for nothing, as before.

The match and co-op clients treat 4429 as a drop, not a refusal: it is outside the web's `REFUSAL_CLOSE_CODES`, so the socket reopens on its backoff ([[R1441]]). The watch page decides by the frame, not the close code: `WatchRoute` takes any `forbidden` frame as a refusal and shows its "can't watch this game" screen without retrying, so a watcher past the budget is told so for good until it reopens the page; the page's wake probe reopens at the pace below, far under the budget, so only an account in a flood meets it. A refused upgrade is not counted, so the window drains and the retry that follows succeeds once the account has room. A normal reconnect is nowhere near the limit: the page's wake probe reopens a socket at most once per `WS_PING_INTERVAL_SECONDS` (15), about four a minute against 300, and a test holds a reconnect loop at that pace for three minutes without a refusal.

Rejected: an HTTP 429 before the handshake, which would turn [[R148]]'s refusals, all of which arrive after the upgrade, into failed handshakes for this one case and need the token verified before the upgrade; caching whole profiles, where a stale ban or a stale pending account would pass [[§9.4]]'s gate; and counting a refused upgrade against the bucket, which would hold a looping client's own window open for ever.

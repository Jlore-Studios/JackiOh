An account may add an authenticator app (a TOTP factor) on its account screen: enrolling shows a QR code and the key, and the factor counts only once a code from the app is typed, which also raises the session to the provider's `aal2`. Signing in by any way (password, email code or link, OAuth) to an account with a verified factor holds the session, in memory only, until the app's code is typed, and keeps only the `aal2` session that comes back; leaving the step revokes the held one. A recovery link for such an account asks for the code before the server is asked whose it is. The server honors a token for an account with a verified TOTP factor only at `aal2`: whether the account has one is read from the provider's user, never from the token, and the last such answer is remembered per user, so an outage cannot lower the bar; an unverified factor does not count. Removing the factor asks first and needs an `aal2` session (the provider's rule). The Data API's reads of a player's own rows are not raised to `aal2`: they reveal nothing the account's owner could not see, and every write goes through the server.

The reuse window is accepted (issue #4041, 2026-11-20): Supabase Auth (GoTrue) v2.197.0 records no used code, so a code stays good for the step before, the step it was made in and the step after (about 90 seconds at a 30-second period with Skew 1), and a new challenge from the same factor takes the same code again inside that window. Using it takes the account's password and a live code seen within about 90 seconds, so it is a narrow, phishing-grade attack. The fix to revisit is the MFA verification attempt hook, a Postgres function refusing a second valid verification of the same factor within 90 seconds, if the projects move to a plan that offers it; reporting it upstream through supabase/auth's SECURITY.md (RFC 6238 section 5.2 says a verifier must not accept a one-time password a second time) stays open for a person and does not block this issue.

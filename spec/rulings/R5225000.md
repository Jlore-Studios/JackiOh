**Why.** After [[R5186000]] detached the snapshot's load, staging's deploy check still timed out twice at 75 s on 2026-11-28 (deploy-staging run 46085619433). Its ask of `GET /api/stats/loading`, a route that never waits on a load, took about 48 s, then answered that no load was under way. The statistics' heavy work was CPU-bound code run straight in async code: `Snapshot::new` in the snapshot's load, and `window_over` cutting a window's figures from the snapshot ([[R3067000]]). On staging's quarter of a processor it held the runtime's threads, so every request waited behind it, and the cut was reported as no load at all.

**Off the runtime.** `Snapshot::new` and `window_over` run through `api::stats::blocking`. On a multi-thread runtime, the server's, it calls `tokio::task::block_in_place`, which hands the worker's other tasks to another thread while the work runs, so the runtime keeps answering other requests while the statistics are worked out. A one-thread runtime has no other thread, so the work runs in place there. That keeps a test's paused clock deterministic: on the blocking pool (`spawn_blocking`, this ruling's first form), the work ran on real threads that a paused test's yields don't wait for. A series game the sweeper started, whose match freezes a win-rate snapshot ([[R3049000]]), then wrote its match row too late for `r333_the_sweeper_runs_every_series_sweep_interval_seconds_on_its_own_and_a_failed_sweep_does_not_stop_it`, which failed twice on pull request #5233.

**The cut.** A shipped patch's window is cut on a task of its own, as the snapshot loads ([[R5186000]]), so a read that gives up leaves the cut to finish for the next. A patch past the snapshot reads its own reach first ([[R4965000]]). The cut counts as the load's last step, "Working out the figures", which `GET /api/stats/loading` reports, so the page's bar and the deploy check follow it. The last load's time stays the snapshot's. A load that begins while another runs keeps the first one's start, so the time shown never runs backwards.

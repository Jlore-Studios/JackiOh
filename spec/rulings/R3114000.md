Every fact the code reads per set is one row of the set table (`set_table!` and `SET_TABLE` in `crates/engine/src/wire/catalog_types.rs`): the set's `SetName` variant and the name it is written as, its stage (`Shipped`, `Held`, `SinglePlayer` or `Custom`), its id segment ([[§5]]; its scripts folder is the segment with `_` between its words), the abbreviation a ruling note's `cards` writes before a `#` (`C+ #12`), and its shadow-ban share ([[R3114001]]). `SetName` is generated from the rows, so its wire names and the client's generated type are as they were. The lists every caller reads are the rows of a stage, in the table's order: `CATALOG_SETS` the `Shipped` and `Held` rows ([[R1420]]), `SHIPPED_SETS` the `Shipped` rows ([[R380]]; the newest shipped set is its last, [[R1371]]) and `SINGLE_PLAYER_SETS` the `SinglePlayer` rows ([[R1846001]]). The shadow ban's sets and ceilings, the deck and trio codes' set offsets (a set's place in the catalog order in thousands, [[R1410]]), `spec check`'s set names, the client's `SetName` and `SHIPPED_SETS` (through the generated `engineConfig.ts`) and `classify`'s and `sweep --due`'s shipped sets read it too, and the cards crate's build takes its set folders from the disk. So a new set is one row appended as `Held`, its census entry and its scripts folder; it ships when its row says `Shipped`.

Rows are appended and never moved or removed: a row's place is its set's place in `SetName`, in the catalog order (so a seeded pick over a pool replays the same, and an old game's replay folds the same, [[R1420]]) and in the deck codes' numbers ([[R1410]]). The table sits directly under `pub const SHIPPED_SETS` and closes with a `];` line of its own, so the sweep workflow's comparison of that range between a push's base and its head still sees a set ship ([[R1678000]]); `classify` and `sweep --due` read a revision from before the table by its old list.

Rejected: making `SetName` a data id read from a table at run time, which would lose the client's generated union of set names; and a JSON table read by an engine build script, which the sweep workflow does not watch and which would need the engine's build to read the disk.

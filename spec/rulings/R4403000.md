[[R1834001]] refused a whole settings write with 400 `bad_request` when one `cosmetics`
pick was not owned, and a shared device could strand an account that way: the device's
stores are not per account, so by [[R634]] the first account's picks go up with the second
account's first save, and every later save resent the same unowned pick and met the same
400. `PUT /api/settings` now keeps out a pick the account does not own instead of
refusing the write for it.

**The keep-out.** A `cosmetics` pick refused as `NotOwned` is never stored: the key keeps
the value the account's stored `cosmetics` group already holds for it, or is left out of
the write when the group holds none. Every other key of the group, and every other group,
merges as [[R634]] says. The answer is the account's copy, as now, and the server logs
`settings.pick_refused` with the profile and the keys. A pick of another kind, one not
offered, and a value that is not text stay 400 `bad_request`, and nothing in the request is
written. The device's own copy of the pick is still drawn through the client's ownership
check ([[R1834001]], What still keeps any text), so the account that does not own it sees
its kind's default, as it does today. The upload of [[R1834000]] already keeps out what an
account cannot wear; the settings write is the only cosmetics write whose refusal could
strand a device.

Hearthstone semantics: a player can equip only what they own, and the server, which holds
what they own, still says so for every pick it keeps (CLAUDE.md rule 7).

Rejected: refusing only the `cosmetics` group and merging the rest, which leaves the group
owed, so the account's own owned picks on that device never land; leaving the refused key
out even when the account holds a pick for it, which replaces the account's own earlier
choice with the default; and a client-only filter by ownership before sending, which older
clients, and any other way a pick goes unowned, would still strand.

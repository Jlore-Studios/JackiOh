The sign-in form's first field takes an email or a username ("Email or username"). What was typed says which it is: a base name never holds `@` ([[R1432]]), so anything with an `@` is an address and goes straight to the auth provider as before ([[§9.4]]), and anything else is a username and goes to the server, `POST /api/auth/username-signin`.

The provider signs in by email alone, and no player may learn another's address, so the server makes that sign-in for the player. It reads the typed name as a claim keys it ([[R1434]]): trimmed and read in NFKC, split at its last `#` into a base and a tag, the base case-folded. `max#3`, ` MAX#3 ` and fullwidth `ＭＡＸ＃３` all name `Max#3`, and a name with no tag names the bare one. It finds the one profile that holds that key and tag and asks the provider's password grant for the session with that profile's address and the typed password. It answers the session (its access token, its refresh token and how long it lives), whether the email is verified (wording only: the gate reads its own, [[§9.4]]) and the authenticator app [[R665]] still asks a code of; never the address. From there it is a password sign-in like any other: the browser holds the provider's session, raises it with the app's code and renews and ends it against the provider ([[§9.2]]). This is the server's one password path. It never signs anyone up, and `/api/auth/signin` still answers only the fixture accounts. It is also the one lookup by username beside the taken-name check and the players tab's search, and the one request that names its caller by username, since it comes before there is a token; [[R1436]] says so, and every request after it keys the player by the token's profile as before.

No such name, text that is no name (`Max#x`), a wrong password and every refusal of the provider's but a rate limit are one 401 with one sentence of their own, "That username and password do not match an account." ([[R160]]). Neither it nor any log line names the address, and no log line names the username. Usernames are shown wherever a player is named ([[R1436]]), so the refusal and how long it takes tell no more than that list does.

Each address ([[R190]]'s) may try `USERNAME_SIGN_IN_ATTEMPTS_PER_WINDOW` (10) username sign-ins per `USERNAME_SIGN_IN_WINDOW_SECONDS` (300), and, counted apart, so may each username. Every try counts, right or wrong. A try its address's limit refuses never reaches the name's. A refusal for either is a rate limit with its wait ([[R192]]), never the 401. The provider's own rate limit is passed on as one, with the whole window as its wait, and a provider that cannot be reached, or whose answer is not a session, is a 503. A username whose limit is spent can still sign in by its email. The provider sees every username sign-in come from the server's address, so its per-address sign-in limit counts them all together, and the operator sizes it for that.

The form words both refusals itself and never shows the server's text: the refusal's sentence, and for a rate limit one that says too many tries came with that username or from this network and to wait a few minutes, the window's length. After a username is refused it offers no confirmation resend and no confirm-first hint: both are for an address, and the player typed none.

Rejected: an open endpoint that tells the browser a username's address, so that the browser could sign in by email itself. It would publish the address of every player whose name is known, and names are shown everywhere.

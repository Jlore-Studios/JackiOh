**Why.** [[R5186000]]'s bar told the time too plainly. It drew nothing until the server's first answer, moved only when a poll answered, sat on a step's share while that step ran, and parked at 95% once a load outran the time to expect, its line reading "1:30 of about 1:02". A bar that stands still reads as a page that stopped. The owner asked for a bar that gives the feel of constant progress.

**The bar.** It shows once the page's read has waited `STATS_LOADING_AFTER_MS`, by the page's own clock, whether or not the server has answered. It redraws every `STATS_LOADING_TICK_MS`, and its fill glides between redraws (`transition: width var(--motion-base) linear`). Its share after `t` is `t / (t + τ)` of `STATS_LOADING_SHARE_MAX`, with `τ` set so the bar stands at `STATS_LOADING_SHARE_AT_EXPECTED` of it at the time to expect. That time is the server's last load time (`expectedMs`), or `STATS_LOADING_GUESS_MS` before any load has finished since the server started. So the bar rises on every redraw, ever slower, however long the load runs, and never reaches the end before the read answers. `t` is the server's elapsed time, carried forward on the page's clock between answers, while the server reports a load, and the page's own wait otherwise. The bar never draws less than it has drawn, whatever an answer says.

**The line.** It names the server's step when the server reports a load, or says "Loading card statistics…" when it does not. Then it gives the time so far, against the time to expect while that is ahead. Once the time to expect has passed, it says the load is almost done ("{elapsed} · almost done") rather than how far it has overrun.

**Unchanged.** The route, the detached load, the retry while a load runs, and the deploy check ([[R5186000]]).

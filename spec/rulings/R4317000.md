A practice seed ([[§14.8]]) was kept with the setup the browser sent, deck and all, and the deck was checked only when the claim settled ([[R1303001]]): the practice session's deal refuses a deck that could never be played, and the settle then marked the seed refused and left the setup on its row. A forged request could send a deck of 128 kilobytes of junk (the API's body cap), hand in an empty game at once, which frees its place among `PRACTICE_SEEDS_OPEN_MAX` ([[R3500001]]), and issue again, so each request left a row that size in the database. [[§14.8]] says the server takes nothing on the client's word in practice, which held for the log and not for the deck it stored.

**What changes.** A seed request deals the game its claim would deal before it writes anything: it builds the config the claim's check builds from the seed and the setup (`economy::practice::config_of`) and runs the practice session's `deal` on it, under the setup's pinned catalog ([[R767000]]) and off the runtime, as the claim's check runs. When the deal refuses, the answer is a 400 `bad_request` that names the engine's reason (an unknown card, a deck that is not `DECK_SIZE` ids, a card past the copy limit), and the request writes no seed, takes no place among the open seeds and holds no database connection or economy lock. So a `cards` deck on a seed is at most `DECK_SIZE` catalog ids, and a row's setup stays about a kilobyte. A `random` deck carries no list and passes as before, and so does every deck the claim would fold. The claim's own check is unchanged, and a seed already stored with a deck the deal refuses is still refused at its claim as `does_not_fold` ([[R1303000]]). The issue and the claim run the one function, so they cannot disagree on a deck. The last board the server keeps for the account ([[R1303003]]) decides no refusal, so the check runs before it is read.

**Reach.** The page already refuses such a deck before it asks for a seed, so an honest player sees no change; a page whose catalog is older than the server's, sending a deck its own catalog refuses, was told only at the claim, after the game, and is now told before it starts, by the answer a seed request that fails always gets: the game earns nothing, in the server's words ([[R2379000]]). The 409s ([[R1483000]]) and their order are unchanged: a catalog the server cannot fold is a 409 before the deal, and a deck it refuses is a 400 before the count.

Hearthstone semantics: a deck that cannot be played is refused when the game is asked for, not after it is played.

Rejected: a SQL check on the size of `setup`, which needs a migration and restates the deck size in SQL (CLAUDE.md rule 9); a bare `cards.len() <= DECK_SIZE`, which bounds the row but still stores unknown or over-long ids the claim refuses anyway and can drift from what the deal accepts; and a config the issue builds apart from the claim's, where an honest deck could pass one and fail the other.

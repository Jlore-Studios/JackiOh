**Why.** The kept snapshot ([[R3067000]]) was dated from when it was first asked for, and a read more than `CARD_STATS_CACHE_TTL_SECONDS` (300) after that took a new, empty cell and began a second load. On staging's quarter of a processor a load runs longer than that, so it finished into a cell no read took again: every later read began the load anew and waited out the client's `API_REQUEST_TIMEOUT_SECONDS`, and two loads ran side by side, as many times the memory as one (issue #5139 found the server killed for memory on this load). Every deploy's statistics check followed the load ([[R5186000]]) and then asked again into a cell already replaced, so staging's deploys failed from 2026-11-27 and production's on 2026-11-27 (issue #5207).

**The age.** The snapshot carries when its load finished, and it is kept `CARD_STATS_CACHE_TTL_SECONDS` from then. While its cell is empty, a load under way or one that failed, it is never replaced: every read joins the load however long it has run, so one load runs at a time, and a read after a failed load makes it again in the same cell. The snapshot that folds the older play versions in ([[R5174000]]) is kept by the same rule. Every window, history, play versions' table and Hall of Fame cut from a snapshot carries the snapshot's time, as [[R3067000]] has them do, so it expires with the snapshot it was cut from, and no figure is older than one TTL from the load that made it.

Rejected: raising the TTL, which only moves the point past which a load never sticks, and keeps every figure longer on a server whose load is quick; and replacing a load still under way after some longer bound, which starts the second load beside the first that this ruling exists to stop. A load that never ends holds every read with it, as the database's own timeouts end it.

The match screen mounts the rematch buttons and the rematch watcher together (`routes/match.tsx`), and each ran its own `GET /api/matches/:id/rematch` every `SERIES_POLL_SECONDS`, so a player on the result screen sent twice the requests the answer needed. Both are the same question about the same match.

**The rule.** The tab keeps one poll for a match id, started by the first component that shows its status and shared by every other. Each answer goes to every listener of the poll, in the order they joined. A component that joins after an answer has come takes that answer at once and sends no request; one that joins before the first answer waits for it. The last component to leave stops the poll, and the next to join starts a fresh one (with its token, so a renewed session is the poll's next token). Two match ids have two polls. The poll is as [[R3205000]] has it: a hidden tab sends nothing, and the tab showing again, or the network coming back, reads once; a wake while a read is out repeats nothing.

**What stays.** The read the buttons make after an offer that did not start a game (the status the player has just changed) is a request the player caused and is sent as it was. A listener's navigation to the new game is its own, as before: the buttons and the watcher each navigate to the game an answer names, and the second finds the player already there (`navigate` to the current path does nothing).

**Presentation only.** CLAUDE.md rule 7: the status is the server's, and which offers meet is the server's call ([[R672]]); the client sends fewer copies of one question.

Hearthstone semantics: both offer buttons of one result screen look at one scoreboard.

Rejected: lifting the poll into `match.tsx` and passing the status down (the buttons and the watcher mount in different places, and the watcher outlives the result panel on purpose, so the screen would own a poll for two children it does not draw); a hook-level `useRef` per component (that is the poll each had); a shared poll keyed by token as well (a renewed token would split one poll in two for the span of a render).

M #50 CN Tech and M+ #2 NA Tech read a win-rate table compiled into the build (`crates/cards/data/win_rates.json`, [[R1101]]), refreshed once per patch by hand-built machinery ([[R1368000]], [[R2386000]]) that never refreshed it: it waited for a patch to reach `PUBLIC_STATS_MIN_LIVE_GAMES` live games, and patches shipped faster than that. Every version since v0.5.9d shipped the same provisional table, so every game's CN Tech added the same card. The owner asked in #3049 that the win rates be live data, not build data.

- **The snapshot.** The figures are the server's windowed card stats ([[R1367000]]), the ones `/stats` shows by default: every counted seat, every mode, under [[R654]]'s gate, each card's in-deck wins and games over its own window at the build's version (`api::stats::win_rate_snapshot`, `win_rates::win_rates_from_report`), read off the report the server already keeps for `CARD_STATS_CACHE_TTL_SECONDS`. As a match starts, the server takes one and hands it to the game as setup (`CreateGameOptions.winRates`), always one, empty when the store cannot answer, so no new game reads a compiled or frozen table. The engine stays pure (CLAUDE.md rule 4): the read is at the game's edge.
- **What a game keeps.** `create_game` keeps the rows a pick can name, `WIN_RATE_SNAPSHOT_ENDS` (4) at each end of the ranking ([[R3049001]]) under the catalog and the pool hold the game plays under ([[R2386001]]), sorted by id (`kept_for_game`), in `GameState.winRates`. A pick passes over at most its own card and the leader, so every pick reads the same card off the kept rows as off the whole snapshot, and a state, every clone the AI searches and a match row carry a few rows, not the catalog's. The snapshot is fixed for the game: every pick reads it, however the live figures move. A Glitch reset deals the new game the same snapshot ([[R676]]).
- **The record.** The match row keeps what the game kept (`matches.win_rates`, migration 0082), and every fold of the match is handed it (`ReplayInput.winRates`: a rebuild, the reaper's fold, a replay, telemetry, a game record's summary), so a fold reaches the same hash anywhere and at any time (§9.3). Keeping kept rows keeps them all, so the refold keeps the same rows.
- **A game handed none.** It reads the frozen table of the shipped catalog its fold runs under ([[R1266000]], [[R1329000]]), else none, and then CN Tech adds Lunar Eclipse and NA Tech fuses Infinite Reserves and Lunar Eclipse ([[R2521007]]). Every record from before this ruling is such a game, so it folds against the table its version shipped with; those tables are frozen and never change again. Duos, practice (in the browser and as the server verifies it), the hotseat, the Sandbox, the dungeon run and the tools are handed none: they have no stats service. A client that has fetched the public figures may hand them (`CreateGameArgs.winRates`).
- **What retires.** `crates/cards/data/win_rates.json`, `cargo jackioh winrates` and its once-per-patch refresh ([[R1368000]], [[R2386000]]'s fill) and the fragment's `winRates` claim ([[R1329000]]): `patches ship` writes no table for the versions it ships, which carry none, so their games read their snapshots. `.github/workflows/winrates-refresh.yml` calls the retired command, and a person deletes it (the bots may not change `.github/`). The owner decided this in #3049 (CLAUDE.md rule 13).
- **What stays.** The card added is hidden from the opponent ([[R440]]); the Radiant face adds it Radiant; a full hand burns it. The snapshot is public aggregate figures and never enters `view_for`, an action or the log.

Hearthstone semantics: a card that reads outside data reads it as the game begins, and the game's record keeps what it read.

Rejected: keeping every row of the snapshot in the state and on the row (every state clone the AI searches would carry the catalog's rows); a table of snapshots keyed by their hash, which the row would name (a second migration and a join on every fold, to save a few rows a match); reading the cache at each pick, which no fold could repeat.

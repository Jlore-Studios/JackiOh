title: A fork screen saves each finished deal and resumes where a cut stopped it (issue #4607)

A fork screen run with `--save <file>` writes one JSON header line naming the set, `--games`,
`--extend`, the budget, `FORK_ROLLOUTS`, `FORK_MAX_PER_GAME`, the catalog version and each
agent's label and `info` answer, then one JSON line per finished deal as soon as it is done: the
deal number, its duel line (which carries the decision times, so the saved string is replayed,
never recomputed), its game record, its trunk hash, its forks (seat, move, both actions) and each
arm's win and fault. A deal is played as a unit — its trunk game, then its forks' arms — and deals
still run in parallel, arms assembling in `(deal, fork, pair, arm)` order; readers sort by deal, so
completion order never reaches the output. A torn last line, left by a killed process, is
dropped, the file rewritten without it, and its deal is played again.

Running the same command again on the same file first refuses a header that differs, naming the
field, then plays its first saved deal's trunk again and refuses the file unless the trunk's hash
and its forks match — one game, catching a rebuilt binary of another AI — then plays only the
deals the file is missing. `--extend` takes its batch stops from the saved deals and the new ones
together. The tally, the duel lines and the records come from every deal's line in deal order, so
a screen played in pieces prints the tally line one uninterrupted run prints, byte for byte. A
finished save, run again, plays nothing and prints its tally again: a screen cannot be grown after
its tally was read ([[R850001]]'s rule against second reads, [[R4319000]]). Without `--save` the
screen behaves exactly as [[R4397000]] reads it.

Hearthstone has no counterpart: there is no public fork screen to tune an AI on.

[[R3727008]] lets `DELETE /api/account` through once a daily game is over "as for any finished match" ([[§9.4]]), but migration 0089 gave the game's two seats `on delete cascade`, so the delete took every finished daily game the account had played: the other player's Daily screen lost it and its board answered 404, while its match and its result stayed and still counted in their record. A daily seat now follows the rule migration 0012 gives a 1v1 seat, as [[R1497000]] gave a co-op seat: once the game has ended, the deleted account's seat on it empties (migration 0100, `on delete set null`) and the game stays. Such a seat reads back as the empty id in both stores, and every daily read (the list, the board, a refused action's game and [[R3934000]]'s read of a game whose moves the purge took) names that opponent `{profileId: "", username: ""}`, as the replay list names a deleted seat, never null and never looked up. The list, the board, its result and its replay ([[R768]]) open as before. The client names that opponent "a deleted account" and offers no Rematch, which the server would refuse anyway, since the friendship went with the account ([[§9.13]]). A running game still refuses the delete, through 0012's `matches_seats_filled_unless_over_check` on its match ([[R3727008]]); this ruling adds no check of its own.

Rejected: keeping the cascade and rebuilding the list's row from the `matches` row, which holds no board, clock or days per move; keeping the deleted id on the seat in the in-memory store, as its 1v1 matches do, which would let the two stores disagree on what a daily game reads back ([[R1497000]]); and looking the empty id up and sending a null opponent, which Postgres refuses (its uuid cast) and the client's `PlayerRef` cannot hold.

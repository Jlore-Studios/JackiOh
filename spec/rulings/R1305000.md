[[§14.5]] says a bar that reaches its size pays and keeps the overflow, in the opening's own
transaction. An opening of a card pack ([[§14.3]]) settles each bar after accruing its spent
duplicates' points ([[R1301002]]):

- **The split** is `settle_bar` (`crates/server/src/economy/tokens.rs`): with `start` points
  before the opening, `gained` from its spent duplicates and `size` the bar's size, `pays` is
  `(start + gained) / size` and the remainder `(start + gained) % size`. A bar past its size,
  which kept counting before bars paid ([[R1301002]]), settles whole: every size it holds pays,
  and the remainder keeps counting.
- **The card token bar** pays `pays` card tokens (`CardToken` under no key). **The cosmetic token
  bar** pays `pays` steps of the cycle ([[R1305001]]).
- **One row per bar per opening.** The paying write replaces the accrual row: one counter row
  with `delta = remainder - start` and reason `token_bar`, not a `pack_open` row beside it. An
  opening that pays nothing keeps today's `pack_open` rows untouched.
- **One transaction.** The payouts are written with the opening's other grants and carry its log
  in their `ref` ([[R1301003]]); every refusal returns before the commit, so a failed opening
  pays nothing.

Hearthstone semantics: Hearthstone turns a duplicate into dust at once; the spec turns spent
duplicates into bar points and pays the bar in the opening that filled it, so the split only
fixes what "keeps the overflow" divides into.

Rejected: paying in a later transaction, which would leave a filled bar readable but unpaid;
carrying the overflow off the bar, which would lose points an account earned; and a counter row
per payout, which would write a bar past its size a row per size it holds.

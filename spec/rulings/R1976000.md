**Why.** Every card figure reads the totals ([[R1044000]]), so a development game's row in `game_records` serves only two things: its detail, for `stats-export` and the notebooks, which [[R1044001]] keeps a week, and its id, which keeps the same game from being counted twice. A development run's own file already holds every game whole, and the owner's PC can play far more games than the database has room for rows: on 2026-10-26 production held 239 MB of the free plan's 500 MB, 125 MB of it `game_records`, while a patch's development totals were about 3 MB whatever its games (800 games 2.7 MB, 32,398 games 3.3 MB).

**The command.** `jackioh-server stats-import --totals-only <file>` reads and checks the file as `stats-import` does, refusing it whole unless every record is a development record under a development id and none is a forced run's ([[R378]], [[R1284000]]). Then, in one transaction, it folds the records into the totals by the same counting ([[R1044000]]) and writes no row of `game_records` for them: no detail, no id.

**Counted once.** The file is the one thing kept: the SHA-256 of its contents, in lowercase hex, is its batch, claimed in `game_record_batches` with how many of its records were folded. A file whose batch is held already folds nothing, and says so. The claim and the counts commit together, so an import that fails leaves neither, and the same file imported again (a job run again, a person's second try) adds nothing. A record whose id `game_records` holds, written a record at a time before or since, its detail emptied or not, is left out, and so is a record whose id the file named before: both are counted. Every figure reads the same as if each record had been imported a record at a time.

**What it does not catch.** Two different files holding the same game: no id is kept, so nothing can tell. The runs that import this way never make such a pair: each learn export's seed base is its own (`learned-<catalog>-<date>-<run>`, [[R1676000]]), and the gather workflow's games are numbered from its run, so two of its runs never play the same game. A person importing by hand imports a file once, as [[R1676000]] already asks of a shard.

This amends [[R378]], under which every development record imported was a row of `game_records`, and [[R1044001]]: a development record imported as totals only has no detail to keep and no id, and its game is read off the run's own file, kept as the run's artifact, for as long as the file is kept.

Rejected: a shorter detail retention for development records, which still writes a row per game and so still grows without end; keeping a hash of each id, about 40 bytes a game, which still grows with the games; a row per numbered series, which the arena's ids (`dev:<patch>:arena:…`, no game number at the end) cannot use; and making `--totals-only` the default, which would change what a person's `stats-import` leaves for `stats-export` without being asked.

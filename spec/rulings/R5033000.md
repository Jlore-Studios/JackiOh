**The key.** When a row's play version first shipped. Each row of `GET /api/stats/versions` also sends `firstShipped`, the position of its first version in the shipped history (`PlayVersionQuery::history`, `patches.json`'s order, the order the versions shipped in, so date order, and the order of micros that shipped on one day), or `null` when the history does not hold it. It sits beside `patches` in `PlayVersionFigures` and `PublicPlayVersion`. The server sends the position because the client cannot order version names (v0.6.4d against v0.6.12b) and must not invent a way to ([[R105]], CLAUDE.md rules 7 and 9); the client compares two integers.

**The sort.** The Sort select on Running and Versions offers Name, Games, Tier, Adjusted and Date, and the Since column's header is a sortable header on both views that sets the same sort. The first press sorts newest first (descending, as every column but Name), the next oldest first. Versions sorts each row by its own first version, so two versions of one card sit apart. Ties keep the order the Cards tab lists the cards in, as [[R3184002]] keeps them (many cards tie: every card unchanged since the same patch); under a Date sort that order is Adjusted in its default direction, whichever direction the Date sort has, so a tied row keeps one place both ways. A row with no position, one from a server deployed before the field, sorts after the rest in either direction, as a row with no figure does ([[R3184002]]). The sort is the page's one sort, kept in the address as `?sort=date` ([[R3184002]], [[R4083000]]).

**The other tabs.** Cards and Tokens offer no Date. On them a Date sort reads as Adjusted in its direction, as Running reads Decisiveness ([[R4678001]]); the page keeps `date` in its state and address, so a switch back to the Experimental tab sorts by it again.

**Why.** The owner asked for the sort. The page already reads a sort key a tab lacks as Adjusted, so one more key costs the other tabs nothing. No new control: one select option and one sortable header, inside [[R4678001]]'s uncluttered page.

Rejected:
- Sorting by version names on the client: it cannot order them, and a parser of its own would restate a rule the server holds ([[R105]]).
- Reading the Cards tab's order in the Date sort's own direction for ties: tied rows would swap places when the direction flips.
- A control of its own for the date: the select and the header already set the page's one sort.

Amends [[R4678001]]'s Rejected "A Since sort" and [[R4680000]]'s list of the sort's keys. Hearthstone has no counterpart.

Amended by [[R5036000]] (issue #5036): the Sort select on Running and Versions offers Name, Games, Tier, Adjusted, Decisiveness, Win rate, Play rate and Date (Win rate and Play rate [[R5037000]]'s), Decisiveness after Adjusted, and the running views no longer read a Decisiveness sort as Adjusted, so they read none of the Cards tab's sorts as Adjusted; a Date sort on the other tabs still reads as Adjusted.

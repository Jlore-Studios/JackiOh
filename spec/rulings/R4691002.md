**Why.** `GET /api/catalog/:version` ([[R388]]) serves the exact snapshot a shipped patch left, the same bytes for everybody, yet it answered `no-store`, so every read reached the container and woke it if it slept. #4011 ruled that nothing in front of the server caches `/api/*`, against cache poisoning: a shared cache keyed on the URL must never keep an answer the request's other parts shaped. A snapshot is not such an answer. Its body depends on the path alone, as [[R163]]'s live catalog's does.

**The rule.**
- A shipped snapshot answers `Cache-Control: public, max-age=CATALOG_SNAPSHOT_MAX_AGE_SECONDS` (a day).
- The Worker answers a `GET /api/catalog/<version>` with no query string from Cloudflare's cache in that data centre when the cache holds it, and never reaches the server for it.
- On a miss, the Worker keeps the server's answer only when that answer is a 200 marked `public`.
- Never kept, and answered by the server every time:
  - `/api/catalog` itself, whose `x-deployed-commit` the deploys' live check polls (CLAUDE.md rule 13);
  - a version the server answers from its live catalog, which stays `no-store`;
  - an unknown version's 404;
  - any other `/api/*` read (#4011);
  - a request with a query string.
- A server test holds #4011's rule for the snapshot: the same bytes and `Cache-Control` whatever headers the request carries. `apps/edge`'s config test allows the Cache API at that one call site and no other.

**Why a day.** A shipped version never reopens, but #1371 once renamed every shipped version, so a version's name has changed what it points at before. A year-long `immutable` would leave a renamed version's old bytes in browsers that no purge reaches. A day still answers every repeat read in a data centre inside it without the server.

**Hearthstone semantics.** None apply; this is hosting.

[[R3792000]] counted only `ApiUnreachableError`, but in production `/api/*` goes through the edge Worker, whose `containerFetch` answers 500 (or 503, 502, 504) for a game server that is crashed, restarting or silent. Those reads rejected as `ApiRequestError`, reset the count and cleared the notice, so the queue screen said "In the queue" with no notice while the server had dropped the ticket.

**The rule.** A read of a wait fails as unreachable when it rejects with `ApiUnreachableError` or with an `ApiRequestError` whose status is at least `FIRST_UNREACHABLE_STATUS` (500, in `routes/play.tsx`). Such reads count together toward `LOBBY_UNREACHABLE_AFTER_READS`. A 4xx (401, 403, 404, 429) still proves the server was reached, clears the notice and resets the count. This replaces R3792000's "a refusal, a 5xx" wording.

**Unchanged.** The threshold, the notice, the ticket logic ([[R897000]]) and presentation only (CLAUDE.md rule 7).

**Rejected.** Listing only 500, 502, 503 and 504, which would let a 501 or a 507 from the edge clear the notice when every 5xx of the Worker means it got no answer; counting 429, which the Worker uses for a throttled container, a server that is alive; counting every rejection, which would make a 401 look like an outage.

Hearthstone semantics: the "Reconnecting…" banner when the connection drops.

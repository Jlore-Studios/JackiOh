Not a rule of the game (CLAUDE.md rule 7): how the client times a run. Hearthstone has no run timer,
so a decision the spec did not make follows the roguelike convention: a run's time is the time it
was played.

The run's clock counts only while a Dungeon page is open and the browser page is shown. The store
adds the session on screen to the run's kept time (`elapsedMs`) on every save, when the page hides
(`visibilitychange`), when it closes or goes to the back-forward cache (`pagehide`) and when the
Dungeon page is left (R2972000's "Back to Play"). Time while the page is hidden, or the page is
away, counts nothing. A reload starts a new session from the kept total, not from when the run
began: a run played five minutes, left ten hours and played five more is ten minutes long. A page
restored from the back-forward cache runs the clock on again. A run kept before this change has
no `elapsedMs` and starts counting when it loads, so no earlier gap is counted. The time the
recorded run holds (`RunRecord.timeMs`, which the fastest-win board ranks by) is that total, and a
clock set back inside a session adds nothing, never less: `DUNGEON_ELAPSED_MIN_MS` floors each
stretch. The on-screen timer shows the same total, the kept time plus the running session.

A settled run is never kept again: hiding the page after it settled writes nothing.

Rejected: timing from `startedAt` by the calendar, which is what made a run paused overnight
read twenty hours; a heartbeat save, so a crash with no `pagehide` loses only the time since the
last save (it undercounts and never overcounts); pausing the clock on the start screen until
Continue is pressed, which would wire the page's own state into the store; and counting only
`visibilitychange` and `pagehide`, which would time a tab left open on another route.

The Campaign's server-checked runs ([[§15.12]]) will need a rule of their own: a clock the device
keeps is not one a leaderboard of checked runs can trust.

The owner's decision (issue #3882, part 3 of issue #3869): the tier pools ([[R3538001]]: S #109 xxFreshJack, S+ #95 JC Backed, S+ #96 Open Enrollment, S+ #97 Selective Enrollment) and S+ #164 KPIs ([[R3538007]]) read current win rates. [[R3538000]] reads them off frozen per-version tables, and none had held live figures: every table from v0.5.8b to v0.5.12k is one provisional table, and since [[R3049000]] no version shipped one, so 213 shipped cards, all 166 of Stinkyscape+ among them, had no record.

- **The refresh.** `cargo jackioh winrates --refresh <report>` reads production's windowed card figures (`jackioh-server stats-cards --window --json`, [[R1367000]]), the ones `/stats` shows and a match's snapshot reads. It is due when the report is at the newest shipped version, no pending fragment carries win rates of record, and no version of the report's patch window (the X a major or a patch opens, [[R1365000]]) shipped any. It then writes a pending fragment carrying each card's in-deck wins and games over its own window (`records`), leaving out the rows under `WIN_RATE_RECORD_MIN_GAMES`, which are never a record, and claiming through `plays` ([[R1366000]]) every card whose script reads the record: a query's `tier`, a scope's `winRateBelow` or the engine's readers (`code_lines::reads_win_rate_record`). There is no games gate: [[R1368000]]'s waited for `PUBLIC_STATS_MIN_LIVE_GAMES` live games on the patch and so never refreshed, and the floor on each row keeps a thin card out. `.github/workflows/winrates-refresh.yml` runs it every day over `STATS_DATABASE_URL`, the read-only connection to production, and opens the pull request.
- **The file.** The fragment claims no catalog card, so `patches ship` names it a micro, which stays inside the X: one refresh per X. Ship freezes the table as `crates/cards/patches/records/<version>.json`, with its blob in `shipped.json` (`recordsBlob`), and no branch edits one, as no branch edits a `win_rates/` table ([[R1329000]]).
- **Who reads it.** The record reads a version's records file before its `win_rates/` table, walking back as [[R3538000]] does, so a refresh moves the record from its version on and no game before it: a game folds against the record of its own version. CN Tech and NA Tech never read it. They read the game's snapshot, else the `win_rates/` table of the shipped catalog a fold runs under, which no version after issue #3049 has ([[R3049000]]). A records file shipped as that table would change what CN Tech added in each of the version's games that had no snapshot (practice, the AI's games, the run) the next time it folded.

Rejected: a refresh every day, a micro a day; a gate on the patch window's games, which a slow patch never clears; reading the live figures during the game, which no fold could repeat ([[R3049000]]).

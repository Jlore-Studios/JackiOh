**Why.** The site's Worker posted `/daily-sweep` every hour (#3727), and each post started a sleeping container: 24 boots a day in each environment, each awake for `SLEEP_AFTER` (five minutes) after it, whether or not the sweep had anything to do. On a quiet site that was most of the container's hours. Yet everything a sweep does is set by stored times it can read in advance: a running game's deadline ([[R3727000]]), each waiting account's next reminder or held email (`decide_notify`), the next invite to lapse ([[R4390000]]'s purge) and the oldest feed row's `NOTIFICATIONS_KEEP_DAYS` ([[R4039000]]). Only a request changes any of them, and a request only ever runs on an awake server.

**The rule.**
- The server answers `GET /daily-next` (outside `/api` and `/ws`, as the sweep's own path is) with the first time at or after now that a sweep has something to do, or null when nothing will until a request changes what is stored. That time is the least of:
  - every running game's earliest deadline (now, for one already past it or a result to write again);
  - for each account a game waits on, `next_notify_at`: the first of now, its games' reminders and the end of its email gap at which `decide_notify` sends it something, each weighed with only the games still running then;
  - the least `expires_at` of any invite;
  - the oldest feed row's time plus `NOTIFICATIONS_KEEP_DAYS`, plus one millisecond.
- When the container's `SLEEP_AFTER` runs out, the Worker's `Server` object asks `/daily-next` (bounded by `DAILY_NEXT_TIMEOUT_MS`) and keeps the answer in its storage, then stops the container as before. A container that starts makes the object forget any kept time, so only the answer of a server that went to sleep is ever kept. A server stopped any other way (a deploy's retire, a crash) left none.
- The hourly cron asks the object to sweep (`sweepDaily`):
  - A running server is swept as before.
  - A sleeping server with a kept time still to come, or a kept null, is left asleep, and the run succeeds.
  - A sleeping server with no kept time, a time that has come, or a storage that cannot be read is woken and swept as before.
- Every loss on time, notification, lapse and purge therefore happens at the same hourly cron it did before. Only an hour with nothing due no longer wakes the server. The cron's schedule, the daily `/readyz` and the sweep itself are unchanged (CLAUDE.md rule 13).

**Hearthstone semantics.** None apply: this is the hosting of [[§9.13]]'s correspondence games, which nothing in Hearthstone has. The decision follows the issue's own rule: keep every timing players and the retention promises see, and spend nothing on hours that do nothing.

Rejected:
- Waking at the kept time with a Durable Object alarm instead of the hourly cron. It would change when things land, not only whether the server wakes, and add a second scheduler beside the cron.
- Leaving the purges out of the due time, which would wake less. It would keep a row past [[R4039000]]'s and [[R4390000]]'s "no longer than" for as long as the site stays quiet.
- Having the Worker read the database itself to decide. That would put the store's queries and a database credential's use in a second place.

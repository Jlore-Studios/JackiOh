A limit on a value a caller could guess counts **guesses**, not requests or frames: one request or frame carries one guess, the one its path or its first field names, and anything else in it (an array, a second field) is read as nothing or refused as malformed, so a batch cannot carry more. Issue #3897's GraphQL aliases put hundreds of guesses in one request past a limit that counted requests; the server has no GraphQL, and this is the lesson held where it applies. `crates/server/README.md`, Guessable values, lists every door that answers right or wrong to a guessed value, with its limit per account and per address ([[R190]]), and a new door adds its line and its test there.

A room's, a co-op room's and a lobby's code is six symbols, 30 bits, and sat behind only the general per-account and per-address request limit ([[R109]]). Now `CODE_TRIES_PER_ACCOUNT_PER_HOUR` (10) distinct codes an account and `CODE_TRIES_PER_ADDRESS_PER_HOUR` (60) an address may try in `CODE_TRY_WINDOW_SECONDS`, across every door that takes the code of a path: `POST /api/rooms/:code/join`, `DELETE /api/rooms/:code`, `GET`, `POST …/join` and `DELETE /api/duos/rooms/:code`, `GET /api/lobbies/:code` and `POST /api/lobbies/:code/enter`. Once either is spent, every lookup from that account or address is 429 `rate_limited` with `details.retryAfterMs` ([[R192]]) until the oldest code tried leaves the window, whatever its outcome: a right code is counted when it is tried, as a wrong one is, so the refusal tells nothing about which codes are held.

Decided here, each with what was rejected:

- A code is counted once per account and once per address in the window, however often it is sent, right or wrong. Rejected: counting every request or every 404, which would lock a player out of a lobby that closed while their screen re-reads it every `LOBBY_POLL_MS`; and counting only the misses, which makes the first refusal tell that a code is held.
- The check and the count are one synchronous step, taken after the lookup and before its answer is given, so requests sent at once cannot all pass a check none has counted yet: past the allowance no more than the allowance are answered, and the rest are 429, a right code among them. Rejected: checking before the lookup and counting after it, which let a burst of parallel requests be answered well past the allowance; counting without refusing, which holds nothing; and refusing only a wrong code, an oracle for the code.
- The people of the code, a room's host and guest, a lobby's members, claim nothing when reading their own, so another account at their address cannot block their own screen. Their cancel of their own room is no guess.
- A malformed code could never be a code's: it is refused unread and counts nothing, as before. A code a challenge's room or a private lobby holds answers the 404 an unknown code does, and is counted when it is looked up, as every code is, so on the join doors too.
- The limits are kept in memory, per server, like the other per-address limits of §9.8. Rejected: reusing the `code_attempts` table, which would need a migration for codes that live minutes.
- No new limit for the daily email's unsubscribe token (a UUID v4, 122 bits, read only from the first `token`, on an open route held to the general per-address request limit) or for socket frames (none checks a guess: `hello` ignores `token`, `matchId` and `roomCode`, and `joinRoom` is malformed). The invite code's limits (`CODE_ATTEMPTS_PER_PROFILE_PER_HOUR`, `CODE_ATTEMPTS_PER_IP_PER_HOUR`) and the username sign-in's ([[R1443]]) already count guesses and are unchanged.

Amends [[R109]] for these doors only: their allowance is the one above beside the general one.

**Why.** With [[R5225000]] and [[R5245000]] in place, staging's deploy of `ae3a355` still failed its statistics check on 2026-11-28 (deploy-staging run 46108101836). Both reads of `GET /api/stats/cards?mode=all` timed out at 75 s, and so did the check's ask of `GET /api/stats/loading` between them, a route that never waits on a load. The whole server had stopped answering, not only the statistics route. The snapshot's load ([[R3067000]]) reads `card_totals` as one stream and decodes each row's figures in async code. sqlx reads its socket with `try_read` and asks tokio for readiness, the one call that spends a task's cooperative budget, only when nothing is buffered. While Postgres keeps the buffer full, which it does whenever decoding is slower than the network, every row is ready at once and the read never yields. Staging's quarter of a processor gives its runtime one worker, so every other request, `/healthz` among them, waited behind the read for its whole length.

**The yield.** The read spends a unit of the task's cooperative budget before each row (`db::pg::next_row`, through `tokio::task::coop::consume_budget`). It hands the worker back to the runtime's other tasks after every budget's worth of rows, 128, and takes them up again where it stopped. The load takes the same time it took. While it runs, the server answers other requests, and `GET /api/stats/loading` reports the load as [[R5186000]] says, so the page's bar and the deploy check follow it to its end.

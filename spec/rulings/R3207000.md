The `/play` lobby's wait read the queue readout ([[R640002]]) every `SERIES_POLL_SECONDS` (2 s), though the server keeps what it counted for `QUEUE_READOUT_CACHE_TTL_SECONDS` (5 s, [[R1996000]]), so most of those reads were answered from the kept count and none of them showed anything new. The readout is a statistic over the last hour; it does not move in two seconds.

**The rule.** The lobby reads the readout once when it opens, as before, and again when a queue is joined (the player has just changed it). While the lobby waits, for a queue or a room, it reads it again every `QUEUE_POPULATION_POLL_SECONDS`, a server constant (30 s) that `cargo test` exports to `apps/web/src/wire/serverConfig.ts` (CLAUDE.md rule 9). It is longer than `QUEUE_READOUT_CACHE_TTL_SECONDS`, so every read counts anew, and far inside `QUEUE_READOUT_WINDOW_SECONDS`, so a count is never visibly late. An idle lobby reads it once and never again.

**What keeps its pace.** The wait's `GET /api/auth/me` read stays at `SERIES_POLL_SECONDS`: it keeps the queue ticket alive, which the server cancels when it goes unheard for `QUEUE_TICKET_STALE_MS` ([[R897000]]), and it is how the wait learns of its pairing. It runs in a hidden tab as before ([[R3205000]]). The readout holds no ticket, so it keeps no such pace; it is not paused in a hidden tab either, since a read every 30 s is cheap and the wait is short.

**Presentation only.** CLAUDE.md rule 7: the readout is informational and never blocks queuing, and the client enforces nothing. The number is the server's, named once in `crates/server/src/config.rs`.

Hearthstone semantics: a queue's "usually under…" line is an estimate, refreshed now and then, not a clock.

Rejected: 60 s (the top of the issue's range, a line that can go a minute stale after a bot fills a queue; 30 s is the low end and costs the server one read in thirty seconds per waiting player); `pollWhileVisible` for it (it would skip the read in a hidden tab and add one when the tab shows, a second rule on a wait whose own timer must keep running hidden, to save one read in thirty seconds); one timer for both reads (the two paces differ by design, and a shared tick would read the readout at the ticket's pace); raising `QUEUE_READOUT_CACHE_TTL_SECONDS` (a server change this issue does not need, since the client now asks less often than the kept count lasts).

`PUT /api/stats/player` stores the account copy in [[R1142000]]'s shape whatever the request holds. It keeps each of `games`, `wins`, `losses` and `draws` that is a whole number of 0 or more. Under `cards` it keeps, for each id the server's catalog holds, those of `played`, `playedAgainst`, `destroyed` and `defeated` that are whole numbers above 0, and drops a card left with none. A whole number is one `Number.isSafeInteger` accepts, so `2.0` is kept as 2. The rest is dropped: every other key, every id the catalog does not hold (a fused or crafted card's generated id and a custom card's among them) and every other value. The answer echoes what was stored. So the public players tab ([[R654]]) only ever names a card that exists, and no text a player wrote reaches it. What `syncPayload` sends is stored unchanged, and the counts stay the client's to report ([[R654]]). A PUT without a `stats` object keeps the stored copy as it is, and a row stored before this keeps what it holds until the player's next sync. Refusing such a PUT with a 400 was rejected: a client that sent one field more would stop syncing.

Follow-up to #3633 (issue #3674). [[R3606000]] sheds a stage on a slow window: `FX_ADAPT_WINDOW` frames whose time passes `FX_ADAPT_SLOW_MS`, or `FX_ADAPT_SLOW_FACTOR` × the display's refresh, a frame. That refresh is taken up to `FX_ADAPT_DISPLAY_MAX_MS` (30 Hz), so a throttled phone that learned a slow refresh passed a second or more of 50–70 ms frames before its first stage, and a moment of the living board ([[R3351000]]) was over before it shed.

**A slow moment sheds within it.** The director also tests runs of `FX_ADAPT_MOMENT_WINDOW` frames, eight, taken from the start of each window: a run whose mean raw frame passes `FX_PHONE_FRAME_BUDGET_MS` ([[R2803000]]'s phone budget) sheds one stage deeper, on every viewport, in [[R3351000]]'s order (motes, then far auras, then the faces past the pointer's own), and a run at exactly the budget sheds nothing. A run and a slow window that end on the same frame shed one stage between them. The particle cap is the slow window's alone: a run never halves it. A set piece's main beats still never shed. Recovery is [[R3606000]]'s: `FX_ADAPT_RECOVER_WINDOWS` healthy windows in a row step one stage back, and a run that sheds starts that count over. The budget is slower than the slowest refresh the window takes for a display's times its slow factor, so a 30 Hz display's healthy frames never shed by it.

Presentation only (CLAUDE.md rule 7): frame times, never game state, an action, `PlayerView` or the log. Hearthstone semantics do not reach frame budgets; no budget, throttle or moment of [[R3351000]] changes.

**Rejected:** a shorter `FX_ADAPT_WINDOW`, which also halves the particle cap sooner and would mistake a 30 Hz display's refresh for load on fewer frames than B34 allows; halving the particle cap on a slow run as well, which would cut a set piece's particles mid-moment for what may be one heavy commit; a run on a phone's director alone, since [[R3606000]] gave every viewport one slow test and one shed order.

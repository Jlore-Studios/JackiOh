## Risks

- **`applySettings` recursion or order:** it receives the new settings `s`, so use `voiceAudible(s)` there, not `readAudioSettings()`. A test that writes then reads should still pass either way, because the store updates before notifying.
- **`master × voice` underflow or `NaN`:** `level()` in `settings.ts` clamps to numbers, so the product is a plain number. A `NaN` product fails `> 0`, which is the safe side.
- **Emotes and `VoicePreview`:** they ignore or already tolerate a false return (`emotes/play.ts:90`), so no change is needed there.
- **Existing tests that set `master: 0` and expect a voice entry:** grep `engine.test.ts` and `cues.test.ts` for `master: 0` and `voice: 0` before editing. If one appears, report it rather than editing the existing test's expectation.
- **Determinism and replay:** none, because this is client audio only and no wasm or engine types change. `apps/web/src/wire` is untouched, so the porcelain check passes.

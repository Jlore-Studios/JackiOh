# Plan (opus, strong)

## Goal

`db (deploy image crates)` (ci.yml's `db-deploy-crates`) took 8m17s on `f50ecdf`, a push to main that changed only `apps/web/`. It was compiling the workspace's crates again even though nothing under `crates/` had changed.

The cause: all three image jobs write one buildx cache scope, `deploy-rehearsal`, and a cache write replaces the scope's whole index with the records of the stages that build built. So each run's `db (deploy image deps)` write (`--target deps`) drops the `crates` and `build` records that the run before wrote. After that, `crates` and the binary are compiled on every run. A toy Dockerfile and the real one show this with buildx's local cache, which has the same index semantics. With one shared cache dir, a second run on the same context compiled all four `jackioh-*` crates again (100 s). With one cache dir per stage, each reading the earlier stages' caches too, the same second run took 20 s and compiled nothing.

Done means two things:
- `rehearse.sh` accepts several caches in `REHEARSAL_CACHE_FROM`, held by a unit test.
- A person gives each stage's CI job its own scope, using the exact `ci.yml` lines under **Open questions**. The bot may not edit `.github/`.

After that, a run that changes nothing under `crates/` finishes the crates job in well under a minute. Locally, every job in the chain stays under about 2.5 minutes on 4 cores:

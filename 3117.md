## Risks

- **Why a rotation and not a card.** My first variant added a duplicate entry to each pool. It broke `filler_deck` and every deck built from the pool ("core-001 appears twice", 7,950 cards tests). A synthetic def would need a script and a catalog row in every set. A rotation changes no def, script or deck, and it moves every draw, which is the effect of a card joining.
- **Replay and determinism.** The shift is 0 unless the feature is on or a test scopes it, so no game changes in any build. The wasm and server builds do not compile it (`testkit` only).
- **Threads.** The thread-local defaults to on in every thread under the feature. `with_pool_shift(0, …)` scopes one thread, so use it only in tests that run on their own thread. `jackioh-tools`' rayon workers are unaffected: its tests passed.
- **What it does not reach.**
  - Pools of one card.
  - The Marketplace's `pool_ids` and the weighted tables (`GRAPE_ODDS`).
  - The web's WebAssembly tests; `apps/web/src/test/seedSearch.ts` is their search.
  - A pool that gets longer rather than moving. Add a second shift only if a miss shows up.
- **Why daily.** The guard compiles the engine with a feature no per-PR group uses. It compiles four crates' tests and then runs the AI's and the server's games, which does not fit the 5-minute job budget. The per-PR check is the engine canary above.

## Risks

- **R1441's wake probe.** `replace()` calls `open()`, so the replacement socket's first view also clears errors. That is intended. The probe's own answer on the *same* socket clears nothing, because the flag is per created socket. The existing R1441 tests prove the probe still behaves.
- **`cancelRetry()` in `connect()`.** The hook's mount effect calls `connect()` after a `close()` in StrictMode remounts, and `close()` already cancels, so the extra call is a no-op there. Do not reset `retry` in `connect()`. Only `onopen` resets it, so an early attempt that fails continues the backoff.
- **Rule 7.** The button only calls `connect()`. It sends no intent and checks no legality.
- **Tests with real timers.** A 1006 drop in `match.test.tsx` schedules a real ~250–312 ms timer. `cleanup()` unmounts, which runs `client.close()` and cancels it, so no test leaks a socket.
- **e2e.** No spec reads the button. `match-status` keeps its text and `data-connection`, because the button sits outside the span.

## Open questions

None block the build. These are the decisions this plan makes, with the alternative it rejects:

- **When the error clears.** It clears on the first `view` of each new socket, not on `onopen`, which fires before `hello` is answered (as the issue argues).
- **What clears.** Every error clears (`error` and `errorCode`), not only `offline`/`transport`. Any error held then describes something from before the fresh view: a server refusal on the old socket was about an intent formed against an older view, and the next `send` or `ack` clears errors wholesale anyway.
- **`connect()` cancels the waiting backoff timer.** The rejected option left it pending, which is harmless but stale and would fire a needless `open()`.
- **Styling.** The button uses the existing `link-button` class and adds no CSS. A person may want touch-target sizing (44 px) on phones later, which is a visual-polish follow-up.

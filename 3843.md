## Risks

- **The cap must hold under concurrency.** The sweep and the notifier task run at once. Only the single conditional upsert keeps them under the cap; never read-then-write.
- **Nothing may be marked sent when an email is skipped.** Otherwise the next day's email would be lost. `daily_notify_sent` still gets only `sent.emailed`.
- **The Postgres contract run could see a stale row.** The new table has no profile FK, so it must be in `TRUNCATE`.
- **Midnight flakiness.** Test 1 passes `now` explicitly. Test 2 pins the clock to noon UTC.
- **Another branch could take migration number 0092 first.** If so, renumber to the next free number and update every list in steps 2–6.
- **No determinism, replay or hidden-information surface is touched.** `decide_notify` and the client are unchanged.

## Open questions

None for a person. These are the decisions the task left open, each with the alternative rejected:

- **Claim before the send, give back on failure.** Rejected: counting after a successful send (two senders could both pass at 49) and never giving back (a Resend outage would burn the day's cap). A timed-out send that Resend did deliver is undercounted by one, which is harmless with 50 to spare.
- **One row per day, `day` as bigint epoch ms** (0089's convention). Rejected: a `date` column as in 0078, and a column on `daily_notify` (per account, so it would need a sum). There is no purge, at one row a day.
- **The cap is a parameter of the store call, not fixed in SQL,** so the contract tests a small cap.
- **The once-a-day log flag lives in memory, per process.** A restart may log once more that day. Rejected: storing the flag.
- **A store error while claiming fails that profile's decision,** as the other store errors in `notify_one` already do. Its push waits for the next sweep.
- **No ruling:** the issue decided option 3, and §9.13's text states it.

## Risks

- **Stale cache.** A view served after the game changed would show the wrong state. The only `self.game` replacement is the `Logged` handler; step 3 greps for others. The restore path builds a new host, so its cache starts empty.
- **Checkpoint and types.** The cache is `serde(skip)` and `ts(skip)`, and its `PartialEq` is always true, so the checkpoint, equality and generated TypeScript are untouched. `DuelOutput::Pushed.views` is skipped the same way, so the JSON-boundary hosts (`boundary.rs`) simply get no views. The actor then falls back to `view_of`.
- **Purity.** Only plain fields in the host value are added: no static, `RefCell` or `Mutex`, which `clippy.toml` bans. The README's "no static, no cache" is about state between calls outside the caller's value; the cache lives in the host and the README line says so.
- **Pinned catalog.** The cache is built inside `step`, which the actor already runs under `engine::run_pinned`, so a cached view and a fresh one use the same catalog.
- **Memory and clone cost.** Each host holds up to two views, and a `Pushed` carries a clone per connected seat. This is far cheaper than a build; check the perf table for any regression.
- **Hidden information.** The watcher frame is built from the seat's own view, as today (no legal actions or forecast, R3477000). Test 3 of `watch.rs` holds this.
